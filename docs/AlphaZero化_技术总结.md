## 〇、一页纸结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | **换 AlphaZero 治不好"送马"** —— value head 只是「特征→胜率」的映射，特征里没有"我的子正被白吃"就永远学不出来 | 同一局面：旧 eval `+36.96 → +37.87`（**反而涨**）；新特征悬子值 `0 → 4.0` |
| 2 | **瓶颈不是算法，是"这一维不存在"** ⇒ 第一步必须是**补特征** | 补完 12 维子力安危后，无论手调权重还是神经网络，送马都会消失 |
| 3 | **钱花在核数，不要花在 GPU** | 产数据 **100% CPU**；`32→64→32→1` 的小 MLP **CPU 甚至更快** |

## 一、算法层：改了什么、没改什么

### 1.1 为什么不能直接搬 ChineseChess-AlphaZero（5 条硬约束）

| # | 约束 | 具体事实 | 性质 |
|---|---|---|---|
| 1 | **二人零和 ≠ 三人棋** | AZ 的 value head 输出 `v ∈ [−1,+1]`，语义是"执子方对唯一对手的胜率"，MCTS backup 依赖 Σv 守恒（零和）。三人棋是**非零和**：我赢 ≠ 另两家输同样多，还会出现"两家都不想打、渔翁得利"。要改就得把 value 变成 **3 维向量 + multi-agent backup**。CCZero 写死 2 人。 | **原理性** |
| 2 | **无 GPU**（本机） | `torch 2.11.0+cpu, cuda.is_available() == False`；原版要 `TF 1.3 + Keras 2.0.8 + Python 3.6` | 硬约束 |
| 3 | **训练成本数量级不符** | 论文每步 1600 次模拟是给 TPU 的；CPU 上 300~800 次模拟 = 每步十几秒到一两分钟；训出能打的价值网络要**数十万~数百万局**自对弈 | 硬约束 |
| 4 | **它不替代规则引擎，而规则引擎才是资产** | AZ 只是"接在规则引擎上的估值 + 搜索层"。本盘的核心难点全在规则：**DXF 变形网格**（格距 13~24，共线判据不能看几何）、**军帐米字格**、**三角区自由回跳**、**副帅/判负/出局三态**、**被将军方强制解将 + 第三方停走**。CCZero 一行都没有。 | **结构性** |
| 5 | **棋盘规模差太多** | 围棋 361 点 / 19×19；本盘 **135 点**，开局 48 子，分支 ~40 ⇒ 大网络的泛化优势用不上，**小模型就够**（反而是好事） | 工程性 |

### 1.2 ★ 核心洞见：换算法治不好"送马"

**老师报的 bug**：推荐引擎让魏右车 `E9→D9` 前进一步，结果魏马 `E8` 被蜀炮 `H2` 白打，无人能保。

**为什么换 AlphaZero 也没用**：

> value head 不是"更聪明的算术"，它只是一个**「特征 → 胜率」的映射**。
> **特征里没有"我的子正被白吃"这一维，网络就学不出来** —— 换什么算法都一样。

**实测（同一局面，客观事实、不依赖任何权重）**：

| 局面 | 旧 `eval` 对魏方评分 | 新特征"悬子值" |
|---|---|---|
| 开局，车 E9 保着马 E8 | **+36.96** | 0.0 |
| 车走 `111→121`（车让开、马无人保） | **+37.87（反而涨了）** | **4.0**＝一个马的整价 |

```
开局   ：112(E8 魏马) 的攻击者 = [E9 魏车（自己在保）, H2 蜀炮]
停车后 ：112(E8 魏马) 的攻击者 = [H2 蜀炮]        ← 唯一的保护者让开了
蜀方合法着法里能吃 112 的：H2→E8（确实存在）
```

**⇒ 第一步必须是补特征，不是换算法。** 这一步做完之后，无论用手调权重还是神经网络，
送马都会消失 —— 因为这次是"这一维终于存在了"，而不是"这一维的权重调多少"。

### 1.3 32 维特征（`server/agents/features_dxf.py`）

| 组 | 维度 | 内容 |
|---|---|---|
| 旧 10 项（保留） | 10 | pressure / danger / urgency / material / check / close1 / close2 / mobility / deputy / gen_lost |
| **★ 新增「子力安危」** | **12** | 悬子值 `my_hanging_val` · 被攻值 · 坏交易 `my_bad_trade` · 被便宜子攻击数 · 悬子数 · 风险平衡 · 对应敌方的 6 项镜像 |
| 合计 | **32** | 全部读 `geometry_dxf` / `rules_dxf`，**没有任何标准二人象棋的假设** |

### 1.4 价值网络（`server/agents/value_net.py`）

| 模型 | 结构 | 特点 | 实测（800 局） | 实测（25 万局后） |
|---|---|---|---|---|
| `logi` | 线性（可解释） | 系数就是权重，能直接读 | AUC 0.6204，矛盾 **0/946** ✅ | AUC 达标，矛盾 **0/363** ✅ |
| `mlp` | 2 隐层（`512→256`） | 能打，非线性 | AUC 0.7511，矛盾 **148/946** ❌ | 矛盾 **0/363** ✅ **可上线** |

**上线门槛（写死，两条同时满足）**：

```
val auc ≥ 0.80   且   mlp 稳健性矛盾 ≈ 0
```

**稳健性自检怎么做的**：用开局 44 手合法着法两两比较，
若两手的特征 **L∞ 距离 < 0.10**（肉眼几乎一样）却给出 **|ΔP| > 0.05** 的预测差 ⇒ 记一次"矛盾"。

> 这一步是**踩坑后加的**：修 `SD_FLOOR` 之前，同一对的 P 差高达 **0.208**，
> 于是"送马那手排第 42/44 名"这个漂亮结论，其实**有相当一部分是在噪声里排名**。

### 1.5 与旧 `eval_dxf` 的对照

| | 旧 `eval_dxf` | 新 `value_net` |
|---|---|---|
| 特征 | 人挑的（10 项，**没有子力安危**） | 32 项（含子力安危） |
| 权重 | **人猜的**（`pressure=0.25` / `material=0.10` …） | **梯度下降从胜负里学出来**（零人工棋理） |
| 训练目标 | 人写的 `battle_score`（斩帅 1000 + 吃子 25 + …） | **真正的胜负结果**（终局唯一活着的将） |
| 结构 | 固定线性打分 | 可学习的 MLP（AlphaZero 的 value head） |

### 1.6 路线图（按性价比排序）

| 阶段 | 内容 | 状态 |
|---|---|---|
| **Phase 1** | 特征 + 价值网络 | ✅ 已完成 |

## 二、资源层：CPU / GPU 的正确用法（AutoDL 实战）

### 2.1 三段任务，资源归属完全不同

| 阶段 | 真正吃谁 | 实测理由 |
|---|---|---|
| ① **自对弈产数据** | **100% CPU** | numba JIT 整数/浮点搜索，**GPU 全程闲置** |
| ② **训练价值网络** | **CPU 更快** | 网络 `32→64→32→1` 才 4 千参数，batch 1024；GPU 的 kernel launch 开销盖过计算。本机 6.4 万样本 CPU 只花 **561 s** |
| ③ （将来）**MCTS + ResNet** | **这里才真吃 GPU** | 每步上千次网络推理、batch 上千 ⇒ 那时再上 4090 |

> ⇒ **"充分运用 GPU"的正确姿势不是堆核**，而是别让 CPU 把喂食者饿死（见 §2.3）。

### 2.2 钱花在核数，不要花在 GPU

| 项目 | 建议 | 为什么 |
|---|---|---|
| GPU | **RTX 3090 24G**（¥1.32/时） | 本轮产数据 100% CPU 活；训练 MLP 规模太小，GPU 反而更慢 |
| **CPU** | **≥12 核，最好 16 核**（选机型时**优先看这列**） | **核数直接决定工时** |
| 内存 | ≥ 32 GB | 16 个 worker 各带棋盘 + numba 工作区 |
| 镜像 | PyTorch 2.x / Python 3.12 / CUDA 12.1 | 依赖只有 `numpy / numba / torch` |
| 磁盘 | 数据放 `/root/autodl-tmp` | 系统盘仅 30G 且不持久 |
| **总花费** | **¥5 ~ ¥15** | 产数据 3h + 训练 10min |

### 2.3 ★★ GPU 占空比铁律：GPU 闲着，先查"喂它的人"

**现象**：GPU 均值 **25.2%**（215 W / 350 W），同期训练轮次还在变慢。

**根因**：守护的训练循环是 **Python 主导**的 —— 小 MLP 单步 matmul 只有**几十微秒**，
被 `zero_grad / forward / backward / step` 的开销淹没 ⇒ 它需要**被及时调度**才能持续喂 GPU。
14 个 CPU 满载的自对弈 worker 一挤，**训练循环就被饿住** ⇒ **GPU 真的闲着**。

**实测（同机、同守护，只改 worker 数）**：

| 自对弈 worker | 数据吞吐（心跳算） | GPU 占空比 |
|---|---|---|
| 14 | 780→794 片 / 123 s = **5.69 局/秒** | **25.2%**（峰 76%，215 W） |
| **8** | 818→831 片 / 122 s = **5.33 局/秒** | **96.2%**（峰 100%，**344 W**） |

⇒ **吞吐只掉 6%（心跳粒度内等同），GPU 涨 71 个点。**

**这条铁律的价值**：它反过来解释了为什么不能"看到 GPU 0% 就以为卡死" ——
**门禁是纯 CPU 任务**（300 局 ≈ 267~381 s），GPU 必然 0%。autopilot 若把
"GPU 连续 360 s < 5%"当故障，就会**腰斩正在正常工作的守护**（这就是 §六 的活锁 bug）。

### 2.4 并行效率：外推时按 40% 折损，不能乘核数

**标定实验**（`tests/_bench_selfplay_throughput.py`，12 逻辑核 / `tl=0.02` / `maxply=250`）：

| 进程数 | 墙钟 | 其中预热 | 纯产局 | **纯产局吞吐** |
|---:|---:|---:|---:|---:|
| 1 | 26.2s | 16.4s | 8.3s | **1.45 局/秒** |
| 4 | 36.8s | 22.8s | 12.0s | 4.00 |
| 8 | 56.1s | 34.5s | 18.4s | 5.22 |
| **12** | **72.6s** | 50.7s | 23.1s | **6.23** |

**核心结论**：单核 0.69 秒/局，12 核线性应是 17.4 局/秒，实测只有 6.23 ⇒ **并行效率仅 36%**。

**已验证不是线程过度订阅**（`NUMBA_NUM_THREADS=1` 结果一模一样 —— 我们的 njit 没有
`parallel=True`，本来就单线程）⇒ 真因是**内存带宽争抢**（每局反复扫全盘 135 点 + DIST 矩阵）。

守护实测更低：**14 进程下每 worker 4.6 s/局，单进程 0.98 s/局 ⇒ 效率 ~21%**。

> ⚠️ 这类任务 40% 的并行效率是正常的，**外推时必须按 40% 折损，不能线性乘核数**。
> Linux 上会更好：`fork` 让子进程白嫖 JIT 预热（本机 `spawn` 下预热占了 70% 墙钟）。

### 2.5 AutoDL 实操要点（详见配置手册）

| 项 | 要点 |
|---|---|
| 机型 | **RTX 3090 24G · 15 vCPU · 90 GiB**；cgroup 配额 `cpu.max = 1500000 100000`（**真配额只有 15 核**） |
| 上传 | `python tools/pack_autodl.py` → `dist/sanchi_autodl_*.zip`（59 文件 / 295 KB，**含整个规则引擎**） |

## 三、训练线架构（三层）

```
cloud_autopilot.sh            ← 调度层（90s 心跳：看进程、看 GPU、补拉起）
   ├── cloud_selfplay.py      ← 数据层（N worker 自对弈 → data/*.parts/partNNNNN.npz）
   └── gpu_daemon.py          ← 训练层（读全部 .parts → 训多档 → 选 best → 门禁 → 落盘）
            └── arena_gate()  ← 裁判层（调 tools/ab_match.py 跑 300 局固定标尺）
```

**关键设计（每条都是踩坑换来的）**

| 设计 | 解决什么 |
|---|---|
| `PartCache` 增量读片（`{(目录,文件名)}` 去重）+ concat 结果缓存 | 不每轮重拼 1200 万样本 |
| **冻结验证集** `val_frozen.json`（稳定键落盘、只读） | 尺子漂移（§六 bug 1） |
| `champion.json` 带 `md5` 指纹 + 启动核验接手 | 冠军随重启归零（§六 bug 2） |
| **对局门禁**：候选 AUC 落在 `≥ best.auc − 0.005` 就开门禁，**升不升级由真棋力说话** | AUC 选不出冠军 |
| **门禁豁免锁** `gate.lock`（`try/finally` 保证删除） | autopilot 活锁（§六 bug 3） |
| **陈旧锁兜底**（>2400 s 自动删） | 守护被 kill 后 autopilot 永久失明 |

**数据规模（收场实读）**

| 数据集 | 分片 | 局数 | 样本 |
|---|---|---|---|
| `selfplay_150k.parts` | 1,130 | — | ~10.7 M（**目录里混了多次运行**，`.json` 只承认 4.55 M） |
| `sp2.parts` | **1,427** | **71,350** | ~2.07 M（50 局/片） |
| **合计** | 2,557 | — | **12,364,743** |

自对弈单局画像：**50 局/片 → 1,250~1,679 样本，胜负有解 32~42 局（判和 16~36%），
平均 131~159 手，耗时 113~127 s/片**。

## 四、裁判系统：三人棋专用的 A/B 对局台

### 4.1 为什么不能跑两批

- **一局三配置**：`{A, B, C}` 同场，**座位轮转** `seat[a] = cfgs[(a-1+g%3)%3]`，每 3 局一轮转
  ⇒ 座位耦合与先手优势被完全对称化。
- ❌ **不能跑两批**（先跑 A 再跑 B）：批次间局面不同，**胜率差里全是运气**。

### 4.2 双指标：只看 `win` 会扔掉一半样本

| 指标 | 定义 |
|---|---|
| 胜率配对 | 三方里谁最终获胜 |
| **序数配对** | `_sc(r,t) = 2 if winner==t else (1 if alive else 0)` |

**三人棋判和率 29~54%** ⇒ 只看 `win` 会扔掉一半以上样本，**必须用序数**。

### 4.3 ★ 噪声地板：先量刻度，再谈显著性

**做法**：同一配置挂两个标签（`x1` / `x2` 指向**同一文件**），两者强度**严格相等**
⇒ 它们之间的一切差异都是**纯噪声**。

| 指标 | 实测（300 局） |
|---|---|
| 胜率 | `x1` 70 : `x2` 57，**p = 0.465** |
| 序数 | 226 : 202，**p 不显著** |
| ⇒ **噪声地板** | **胜率 ±4 点 / 序数 ±24 分** |

**地板是全篇的刻度尺**：没有它，任何 p 值都没有参照物。

### 4.5 ★ 一个反直觉但被证实三次的规律

> **三人棋的"棋力"没有绝对值，只有"对谁"。**

同一份权重 `v1233`：

| 阵容 | 战绩 | 判和率 | 解读 |
|---|---|---|---|
| `{n, v, bal}` | **32~37%**（p≤0.007） | 29~31% | 强 |
| `{n, v, v}` | 12~14%（三方全平） | 48~54% | 打平 |

**机制**：两台"和平型"同场 ⇒ 对局从 176 手拉长到 **226 手**、判和率 **31% → 54%**
⇒ 双方优势都变成和棋，**场上那台贪吃的纯搜索反而吃掉两家的子**。

⇒ **"同款互打打平" ≠ "它不强"**（任何策略都打不过自己的复制品）；
`{2纯+1价值}` 稳赢，`{1纯+2价值}` 优势转负。
**这就是"按座位配"（吴方开、魏/蜀关）的实证依据 —— 而不是"全局一刀切"。**

## 五、战术与落子权重

### 5.1 旧 `eval_dxf` 的 10 项权重（`DEFAULT_W`）与致命缺陷

| 项 | 权重 | 测什么 |
|---|---|---|
| `pressure` | **0.250** | 我压向敌帅的压强（**√子力加权**） |
| `danger` | **0.100** | 敌压向我的压强 |
| `urgency` | **0.050** | 进攻权重随时间上升 |
| `material` | **0.100** | 我 − **最强的那一个**对手 |
| `check` | **120.0** | 将军 |
| `close1` / `close2` | **400 / 80** | 有子贴到敌帅 1 / 2 步内 |
| `mobility` | **0.02** | 可走着法数 |
| `deputy` | **6.0** | 手握副帅 |
| `gen_lost` | **50.0** | 自家帅没了 |

**两个致命缺陷（这就是"送马"的直接成因）**：

1. **`material` 权重只有 0.10，且只跟"最强的那一个"对手比** ⇒
   一匹马只值 `0.1 × 4 ≈ 0.40` 分，而 `close1` 是它的 **1000 倍**；
   而且**吃弱者的子贡献 0**（因为只跟最强对手做差）。
2. **整张表没有一维在管"我的子会不会被吃"** ——
   `pressure` 只算"敌帅射线上"的压强，马被白吃时它**一分不动**。

⇒ 所以 `111→121`（车让开、马无人保）时 `eval` 从 **+36.96 涨到 +37.87** —— 它认为这一步**更好**。

### 5.2 λ（价值网络混合权重）的边界 —— 必须 ≤ 0.5

| λ | 结果 | 判决 |
|---|---|---|
| **0.15** | 192 序数 | ≈ 0.35 |
| **0.35** | **243 序数** | ★ **采用** |
| 0.60 | 128 序数 | 明显差 |
| **0.85** | **12 序数**（96% 被斩、平均 126 手结束） | **灾难** |

**混合实现的两个坑**：

1. **z-score 归一化 + `SD_FLOOR = 0.10`**：特征已手工归一化，再除以 batch std 会把
   "几乎不变的维度"放大几十倍 ⇒ 锁住最大增益 10 倍内（同一对的 P 差 **0.208 → 0.061**）。
2. **有效 λ 会浮动**：z-score 使实际混合比例随局面变化 ⇒ 不能只看名义 λ。

**落地方式（按座位，而非全局）**：

```json
// server/agents/agents.json
"players": {
  "1": { "use_value": false },                    // 魏：关
  "2": { "use_value": true, "value_lambda": 0.35 }, // 吴：开
  "3": { "use_value": false }                     // 蜀：关
}
```

依据：`{2纯+1价值}` 稳赢、`{1纯+2价值}` 优势转负（§4.5）。

### 5.3 ★ 推荐档位：9 plies 是"金发姑娘区"

| 档 | 实测耗时 | 结论 |
|---|---|---|
| 6 → 9 | — | **值钱**：中位 ratio **3.54**（16 个局面里 12 个真变招） |
| **9** | **0.05 ~ 1.8 s（秒回）** | ★ **智力饱和点 / 默认档** |
| 9 → 12 | **43.19 s**（3345 万节点） | **无收益**：ratio **1.00**、噪声占 **45%**、耗时 **×24** |
| 12 → 15 | **639~731 s** | 噪声级：选招只差 **0.04 / 0.06 分**（估值量级 4031 ≈ 0.001%），代价 **×20** |

⇒ **瓶颈不是"深度不够"，是"估值函数分不开这几手"**；再加深只是把噪声重洗一遍。

**当前配置**：

```python
# server/match.py
HINT_BUDGET = {9: 12.0, 12: 150.0, 15: 720.0}   # 秒
HINT_PLIES_DEFAULT = 9                            # 2026-10-02 老师定
```

⚠️ **两批标定在本档位上是矛盾的**（批一 2 局面说"9 弱"、批二 16 局面说"9 够"），
已一并留档；**采信批二**（样本量大一个数量级 + 与老师体感一致）。

### 5.4 "和平型"弱点（已定位，未修）

价值 Bot 的**吃子收益只有纯搜索的 1/3**（`81,414 vs 223,677`），**斩帅少、被斩多**。

已定位两处根因：

1. **混合用 z-score + `SD_FLOOR=0.10`** ⇒ 有效 λ 浮动；
2. **训练标签把判和局整局丢弃** ⇒ 网络学不到"如何结束一盘棋"。

### 5.5 其他与"权重/门槛"相关的参数

| 参数 | 值 | 含义 |
|---|---|---|
| `YARD_MARGIN` | **25** | 门禁升级门槛（序数分） |
| `YARD_SEED` | **2200000** | 固定标尺种子（可复算） |
| AUC 筛子 | `≥ best.auc − 0.005` | 不选冠军，只决定"要不要开对局门禁" |
| `ROOT_KEEP` | `{3:99, 6:14, 9:8, 12:5}` | 根节点宽度限制 |
| `REPEAT_LIMIT` | **3** | 重复着法判罚（无向边计数） |
| `W_SLAIN` | **1000** | 综合分里"斩帅"的权重（吃副帅**不得**误加） |
| `STALEMATE_ROUNDS` | **9** | 残局自动判平的轮数 |
| `SD_FLOOR` | **0.10** | z-score 增益上限（防放大噪声） |
| 上线门槛 | `auc ≥ 0.80` 且 `mlp 矛盾 ≈ 0` | 两条同时满足 |
