## 一、★ 最重要的一个发现：**换成 AlphaZero，「送马」照样存在**

老师在 2026-10-01 报了一个 bug：推荐引擎让魏右车 E9→D9 前进一步，  
结果魏马 E8 被蜀炮 H2 白打（无人能保）。当时已查明根因在估值权重。

**现在要把这件事说得更狠一点：**

> **AlphaZero 的 value head 不是"更聪明的算术"，它只是一个「特征 → 胜率」的映射。**  
> **特征里没有"我的子正被白吃"这一维，网络就学不出来 —— 换什么算法都一样。**

### 证据 ①：旧估值函数的 10 个计分项，逐项列出，没有一项管子力安危

`server/agents/eval_dxf.py` → `DEFAULT_W`：

| 项                   | 权重        | 它测什么                   | 能表达"马被白吃"吗      |
| ------------------- | --------- | ---------------------- | --------------- |
| `pressure`          | 0.250     | 我压向敌帅的压强（**用 √子力 加权**） | ✗               |
| `danger`            | 0.100     | 敌压向我的压强                | ✗               |
| `urgency`           | 0.050     | 进攻权重随时间上升              | ✗               |
| `material`          | **0.100** | 我 − **最强的那一个**对手       | ✗（权重极低 + 只跟最强比） |
| `check`             | 120.0     | 将军                     | ✗               |
| `close1` / `close2` | 400 / 80  | 有子贴到敌帅 1/2 步内          | ✗               |
| `mobility`          | 0.02      | 可走着法数                  | ✗               |
| `deputy`            | 6.0       | 手握副帅                   | ✗               |
| `gen_lost`          | 50.0      | 自家帅没了                  | ✗               |

**结论：这是"我想不想快点击杀敌帅"的模型，不是"我的子会不会丢"的模型。**  
两个马被白吃，`pressure` 一分不动（马不在 e 方帅的射线上），  
`material` 也几乎不动（权重 0.1，且只要不是最强对手就不计）。

### 证据 ②：实测（今天现算的）

| 局面                   | 旧 `eval` 对魏方的评分       | **悬子值**（新特征）     |
| -------------------- | --------------------- | ---------------- |
| 开局，车 E9 保着马 E8       | **+36.96**            | **0.0**          |
| 车走 111→121（D9）后，马无人保 | **+37.87** ← **反而涨了** | **4.0** ← 一个马的整价 |

攻击者名单也随之变化：

```
开局   ：112(E8 魏马) 的攻击者 = [E9 魏车（自己的车在保）, H2 蜀炮]
停车后 ：112(E8 魏马) 的攻击者 = [H2 蜀炮]          ← 唯一的保护者让开了
蜀方合法着法里吃 112 的：H2→E8（确实存在）
```

**旧 eval 看不见这 4 分的悬空，因为它**根本没有这个特&#x5F81;**。**

### ⇒ 所以第一步必须是「补特征」，不是「换算法」

我今天做的就是这个（§四）。补完特征之后，**无论用手调权重还是神经网络，送马都会消失** ——  
因为这次是"这一维终于存在了"，而不是"这一维的权重调多少"。

## 二、ChineseChess-AlphaZero 为什么不能直接搬（5 条硬约束）

| # | 约束                             | 具体事实                                                                                                                                                                                                                              | 性质  |
| - | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| 1 | **二人零和 ≠ 三人棋**                 | AZ 的 value head 输出 `v ∈ [−1, +1]`，语义是"**执子方**对唯一对手的胜率"；MCTS 的 backup 依赖 Σv 守恒（零和）。三人棋是**非零和**：我赢不等于另两家"输同样的量"，还可能出现"两家都不想打、渔翁得利"（这个现象在本项目 `eval_dxf.py` 的注释里已经被记录过）。要改就得把 value 变成 3 维向量 + multi-agent backup。**CCZero 写死了 2 人。** | 原理性 |
| 2 | **无 GPU**                      | 本机 `torch 2.11.0+cpu, torch.cuda.is_available() == False`。原版要 `tensorflow-gpu 1.3.0 + Keras 2.0.8 + Python 3.6.3`，README 明说"需要分布式 + 巨大算力"                                                                                         | 硬约束 |
| 3 | **训练成本数量级不符**                  | 论文每步 1600 次模拟是给 TPU 的；CPU 上 300~~800 次模拟 = 每步十几秒到一两分钟。要训出能打的价值网络需要\*\*数十万~~数百万局\*\*自对弈                                                                                                                                            | 硬约束 |
| 4 | **它不替代规则引擎 —— 而规则引擎才是我们真正的资产** | AZ 只是"接在规则引擎上的估值 + 搜索层"。本盘的核心难点全在规则：**DXF 变形网格**（相邻点格距 13~24，共线判据不能看几何）、**军帐米字格**、**三角区自由回跳**、**副帅/判负/出局三态**、**被将军方强制解将 + 第三方停走**。这些 CCZero 一行都没有，**换 AZ 一样得我们自己写，一行都省不掉**。                                                       | 结构性 |
| 5 | **棋盘规模差太多**                    | 围棋 361 点、19×19；本盘 **135 点**，开局 48 子，分支 ~40。局面多样性远低于围棋 ⇒ 大网络的泛化优势用不上，小模型就够（反而是好事）                                                                                                                                                  | 工程性 |

**再加一条现实约束**：CCZero 是 2017 年的栈（TF 1.3 / Python 3.6），  
本机是 Python 3.12 + torch 2.11 ⇒ 装起来就是一场硬仗，收益还未知。

## 三、那"搜索树"目前的真实水平（我今天核实的）

`server/agents/search_bot.py`（896 行）已经是**相当完整**的引擎：

| 机制                                    | 有没有             | 说明                                    |
| ------------------------------------- | --------------- | ------------------------------------- |
| Paranoid minimax（三方都当敌人） + alpha-beta | ✅               | 三人棋的标准做法                              |
| **代数记谱 PVS（零窗口搜索）**                   | ✅               | `EPS = 1e-3`，注释里还记着浮点精度坑              |
| **迭代加深**                              | ✅               | 从浅到深，超时停在上层，永远有答案                     |
| 杀手着法 + 历史启发                           | ✅               | `_killers` / `_hist`                  |
| **静态搜索（quiescence）**                  | ✅               | 消除水平线效应                               |
| 宽度限制（`width_for`）                     | ✅               | 按 plies 收窄根节点                         |
| numba JIT（`nb_core`）                  | ✅               | 7 张走法表全直接读 `rules_dxf`，零自建表           |
| **置换表（TT / zobrist）**                 | ❌ **没有**        | 全文件 grep 无 `zobrist/transposition/tt` |
| **MCTS / PUCT**                       | ❌ 没有            | 纯 alpha-beta 系                        |
| **神经网络估值**                            | ❌ 没有（今天刚建，见 §四） | 原来是 `eval_dxf` 手调权重                   |

**⇒ 结论：现在的搜索树不是"旧"，是"缺件"。缺的是 ① 置换表 ② 学出来的估值。**

### 置换表的收益，我今天实测了一下

`tests/_probe_transposition.py`：从真实中局出发做有界穷举，数"同一局面被不同着法顺序重复展开"的比例。

| plies | nodes（路径数） | distinct（不同局面） | 重复率      |
| ----- | ---------- | -------------- | -------- |
| 1     | 39         | 39             | 0.0%     |
| 2     | 1,155      | 1,155          | 0.0%     |
| 3     | 47,191     | 43,259         | **8.3%** |
| 4（截断） | 161,522    | 149,231        | **7.6%** |

**这只是保守下界** —— 它只数了"同层内不同顺序到达"，没数真正的 TT 还能省掉的  
"**不同深度到达同一局面**"（那部分更大）。而且三人棋的 TT 还要把"重复判罚相关历史"并入键，  
不能只 hash 棋盘。**但 8% 已经是白捡的。**

## 四、今天已经落地的一步（AlphaZero 的「形」）

老师要的"不用旧的手调权重"，今天做出来了 —— 用的是**这台机器训得动**的版本。

### 新增三个文件

| 文件                              | 作用                                                                   |
| ------------------------------- | -------------------------------------------------------------------- |
| `server/agents/features_dxf.py` | **32 维特征**。旧 10 项 + **新增 12 项"子力安危"**（悬子值/被攻值/坏交易/被便宜子攻击数/悬子数/风险平衡…） |
| `server/agents/value_net.py`    | **价值网络**。`LogiNet`（线性，**可解释**）+ `MLPNet`（2 隐层，能打）。纯 CPU 训练           |
| `tests/_train_value_net.py`     | **自对弈训练管线**。产数据 → 用胜负标签训练 → 报告 + 存盘                                  |

### 与旧方案的对照

|      | 旧 `eval_dxf`                             | 新 `value_net`                    |
| ---- | ---------------------------------------- | -------------------------------- |
| 特征   | 人挑的（10 项，**没有子力安危**）                     | 32 项（含子力安危）                      |
| 权重   | **人猜的**（pressure=0.25 / material=0.10 …） | **梯度下降从胜负里学出来**（零人工棋理）           |
| 训练目标 | 人写的 `battle_score`（斩帅1000 + 吃子25 + …）    | **真正的胜负结果**（终局唯一活着的将）            |
| 结构   | 固定线性打分                                   | 可学习的 MLP（AlphaZero 的 value head） |

### 学习结果（400 局自对弈）

## 五、实测数据

### 5.1 数据规模

| 项     | 值                                           |
| ----- | ------------------------------------------- |
| 自对弈局数 | **800 局**（`tl=0.03`，含 12% ε 随机走子）           |
| 产数据耗时 | **561 s**（约 0.7 s/局）                        |
| 有效样本  | **64,529** 条（只在**分出胜负**的局上取标签，570/800 局有胜者） |
| 正例率   | 0.431（三条军各约 1/3 机会赢）                        |
| 训练/验证 | 54,849 / 9,680                              |

### 5.2 验证集指标

| 模型              | AUC        | 准确率        | base（全猜多数类） | BCE    |
| --------------- | ---------- | ---------- | ----------- | ------ |
| `logi`（线性）      | 0.6204     | 0.6110     | 0.5741      | 0.6631 |
| **`mlp`（2 隐层）** | **0.7511** | **0.7066** | 0.5741      | 0.5798 |

**怎么读**：AUC 0.75 = 随机抽一对「赢家局面 / 输家局面」，网络有 75% 概率把赢家的排前面。  
比瞎猜（0.5）明显好，但**离"能打"还远**（AlphaGo Zero 级别的 value net AUC 在 0.9+）。

### 5.3 ★ 稳健性自检（这一步是踩坑后加的，很关键）

用开局 44 手合法着法做**两两比较**：若两手的特征 L∞ 距离 < 0.10（肉眼几乎一样），  
却给出 |ΔP| > 0.05 的预测差 ⇒ 记一次「矛盾」。

| 模型     | 矛盾对数            | 最严重的一对                                      |
| ------ | --------------- | ------------------------------------------- |
| `logi` | **0 / 946 ✅**   | —                                           |
| `mlp`  | **148 / 946 ❌** | `111→121` vs `111→131`：特征差 0.06 → P 差 0.061 |

**这是一个必须坦白的发现。** 修 `SD_FLOOR` 之前更糟：同样这一对，P 差高达 **0.208**，  
于是"送马那手排第 42/44 名"这个看起来很漂亮的结论，其实**有相当一部分是在噪声里排名**。

根因两条：

1. **标准化放大**：我们的特征已手工归一化，再除以 batch std 会把"几乎不变的维度"放大成几十倍增益  
   → 已用 `SD_FLOOR = 0.10` 把最大增益锁在 10 倍内（P 差 0.208 → 0.061）
2. **数据不够 + 标签噪声大**：同一个局面"最后是否获胜"本身噪声极高  
   （同一局面，后续走得不同就可能是赢是输）⇒ 6.4 万样本撑不起 32 维非线性模型

### 5.4 但方向是对的 —— 送马那手，两个模型都给**更低**的胜率

| 局面                    | 悬子值     | 旧 `eval`        | `logi`     | **`mlp`**        |
| --------------------- | ------- | --------------- | ---------- | ---------------- |
| ① 开局（车 E9 保着马 E8）     | 0.0     | +36.96          | 0.354      | 0.340            |
| ② 走 111→121（车让开、马无人保） | **4.0** | **+37.87（涨）**   | 0.339      | **0.252**        |
| **ΔP**                |         | **+0.91（认为更好）** | **−0.015** | **−0.088（认为更差）** |

**结论**：

- ✅ **特征层是确定的胜利** —— 悬子值 0 → 4.0，这是**客观事实**，不依赖任何训练，也不依赖任何权重怎么调。
- ⚠️ **价值网络方向对、但还不够硬** —— MLP 给它 −0.088（正确方向），  
  可是它同时有 148 对矛盾 ⇒ **现在还不能拿它去上线排名**。
- ⇒ **瓶颈不在算法，在数据量与算力。** 这正是老师提的云端 GPU 能解的地方（见 §七）。

## 六、落地路线图（按性价比排序）

### Phase 1 ✅ 已完成 —— 特征 + 价值网络

「不手调权重」已经做到。**下一步是把它接进对弈/推荐**（见 Phase 1.5）。

### Phase 1.5 ★ 两条路，我建议**先走 (a)**

**(a) 只把「子力安危」这一组特征接进现有估值**（半天，零风险）  
—— 特征层已经被实测证明是可靠的（悬子值 0 → 4.0 是客观事实）。  
给 `eval_dxf` 加一项 `risk`（悬子值 + 坏交易），权重先用保守值（如 −6/分），  
送马**当场消失**，且不引入任何训练噪声。  
⚠️ 这需要老师松口："手调权重"不再扩充 —— 但这里加的是**已经验证过的特征**，  
不是又一次"猜权重"。而且它是 (b) 的地基。

**(b) 把学到的价值网络接进 `SearchBot` 的叶子估值**（需先解决 §5.3 的稳健性问题）  
**与旧 `eval_dxf` 并存可切换**：

- 推荐功能（`/api/hint`）先用它 —— **风险最低**，只影响建议、不影响对局
- 观察一段时间，确认不劣于旧口径，再切对弈 Bot
- 要点：JIT 内核（numba）里跑不了 torch ⇒ 两条路  
  (a) **把学到的权重导出成系数表**，用 numba 版线性打分（若用 LogiNet，几乎零成本）  
  (b) MLP 则在 JIT 外做叶子估值（会拖慢，适合"推荐"这种低频调用）

### Phase 2 （1~2 周）置换表 TT + 迭代加深的配合

- 三人棋的 TT 键要小心：**重复判罚依赖历史**（《长将判负》），  
  不能只 hash `board + turn`，得把"最近若干手的边"一起进键，否则会拿到错的缓存分数
- 收益：保守 8%（同层）+ 更多（跨层）；且**能顺带缓解"反复走同一路径"的搜索盲区**

### Phase 3 （1~2 周）MCTS / PUCT 替换或并挂

- **为什么值得**：paranoid 假设"另两家**联合**针对我"，在三人棋里过于悲观 ——  
  现实中另两家也在互相算计。MCTS 的 multi-agent backup 能表达"我赢即可，别人谁高谁低无所谓"
- **怎么做**：policy 先验用现成的着法排序（杀手/历史/静态序）；叶子估值用 Phase 1 的价值网络
- 这一步才是"用 AZ 的算法"，但**必须建立在 Phase 1.5 之上**（否则叶子估值还是那套看不见悬子的式子）

### Phase 4 （有 GPU 才谈）CNN 双头网络

真 · AlphaZero：ResNet + policy head + value head，自对弈迭代。  
本机无 CUDA，**不建议现在投入**。

## 七、★ 云端 GPU（AutoDL）能解开什么 —— 老师提出后，这是立刻可做的

老师说「我可以在云端 GPU 上帮你跑，例如 autorl，AutoDL，可以吗？」—— **可以，而且卡在点子上。**

### 7.1 GPU 究竟解哪个结？—— 不是"算得更快"，是"能喂得起数据"

| 瓶颈       | 本机（CPU）现状                        | 上 GPU 后                                         |
| -------- | -------------------------------- | ----------------------------------------------- |
| **数据量**  | 800 局 / 6.4 万样本，AUC 0.75、148 对矛盾 | **10 万局 / 400 万样本**（16 核并行自对弈，实测外推 ≈ **3 小时**）  |
| **网络容量** | 只能上 MLP（32→64→32→1）              | 可以上 **ResNet 双头（policy + value）**，真正的 AlphaZero |
| **训练迭代** | 单次训练分钟级，勉强能调                     | 秒级/epoch，可以做完整 self-play ↔ train 闭环（几十轮迭代）      |
| **标签质量** | 一局一个胜负，噪声大                       | 可以引入 **TD(λ) / 多局平均 / MCTS 访问分布**做软标签，噪声大幅下降    |

**⇒ 换句话说：本机已经把"该有的零件"（规则引擎 + 特征 + 训练管线 + 自对弈）全部装好了，  
缺的只是"算力和数据量"。云端 GPU 补的正是这一块。**

| `docs/AutoDL_配置与操作手册.md`  | 买什么、怎么装、怎么跑、几个坑                                        | —                                            |

### 7.2.1 ★ 本机实测标定（决定买几核的唯一依据）

`tests/_bench_selfplay_throughput.py`，12 逻辑核 / `tl=0.02` / `maxply=250`：

|    进程数 |        墙钟 |  其中预热 |   纯产局 |    **纯产局吞吐** |
| -----: | --------: | ----: | ----: | -----------: |
|      1 |     26.2s | 16.4s |  8.3s | **1.45 局/秒** |
|      4 |     36.8s | 22.8s | 12.0s |         4.00 |
|      8 |     56.1s | 34.5s | 18.4s |         5.22 |
| **12** | **72.6s** | 50.7s | 23.1s |     **6.23** |

**核心结论：并行效率只有 36%**（单核 0.69 秒/局，12 核线性应是 17.4 局/秒，实测 6.23）。  
已验证**不是**线程过度订阅（`NUMBA_NUM_THREADS=1` 结果一模一样 —— 我们的 njit 没有  
`parallel=True`，本来就单线程）⇒ 真因是**内存带宽争抢**（每局反复扫全盘 135 点 + DIST 矩阵）。  
这类任务 40% 的并行效率是正常的，**外推时必须按 40% 折损，不能线性乘核数**。

Linux 上会更好：`fork` 让子进程白嫖 JIT 预热（本机 spawn 下预热占了 70% 墙钟）。

### 7.2.2 ★ 一个"必须扩数据"的铁证

同一套特征，**小样本下系数会翻符号**：

| 特征                      | 24 局训练    | 800 局训练   | 结论         |
| ----------------------- | --------- | --------- | ---------- |
| `my_bad_trade`（我的坏交易）   | −5.03     | −4.72     | 稳定 ✅       |
| `my_hanging_val`（我的悬子值） | **+4.72** | **−3.27** | **符号翻转 ❌** |

一个"我的子正被白吃"的指标，在小样本里竟然学成了**正分**。  
⇒ 800 局根本不够让网络把这一维的方向学稳。**这不是算法问题，是数据量问题。**

### 7.2.3 云端落地流程（照手册做）

```
① python tools/pack_autodl.py                    # 本机打包 → dist/*.zip
② AutoDL 无卡模式上传解压 + pip install -r requirements_cloud.txt
③ python tools/cloud_selfplay.py --games 100000 --workers 16 --out data/selfplay_100k.npz
④ python tools/train_cloud.py --data data/selfplay_100k.npz --tag 100k
⑤ 下载 server/agents/values/value_*_100k.json + *.report.json 回本机
```

**训练报告里必须看的两个数**：`val auc`（目标 ≥ 0.80）与  
**`④ 稳健性自检`**（`mlp` 矛盾对数必须掉到接近 0；本机 800 局是 148/946 ❌）。  
**自检没过就不许上线** —— 那说明网络在噪声里排名。

### 7.3 三人棋必须做的改造（**不能照抄 CCZero**）

| 项             | CCZero（2 人）      | 我们要改成                                             |
| ------------- | ---------------- | ------------------------------------------------- |
| value head 输出 | 1 维 `v ∈ [−1,1]` | **3 维**（三方各自胜率），或 "我赢/和/输" 3 类                    |
| MCTS backup   | 零和，`−v` 直接回传     | **multi-agent backup**：每家独立累计，不取负                 |
| 和棋/判负         | 简单               | 要接我们的 **认输 / 判负 / 出局 / 残局自动判和 / 重复着法判罚**          |
| 规则引擎          | 标准象棋             | **DXF 变形网格 + 军帐米字格 + 三角区回跳 + 副帅**（我们已有，CCZero 没有） |


### 7.4 我建议的 GPU 使用顺序（性价比）

1. **先扩数据**（不动算法）：10 万局自对弈 → 重训 MLP → 看 AUC 能否从 0.75 上到 0.85+  
   —— 成本最低、最可能直接见效，也最能验证"数据量就是瓶颈"这个判断
2. **再上 ResNet value head**：网络容量跟上
3. **最后加 policy head + PUCT MCTS**：这才是完整 AlphaZero（Phase 3）
4. ⚠️ **别一上来就上完整 AlphaZero**：三方规则改造 + MCTS 正确性验证的坑很深，  
   先把"数据 + value net"这条最短路径打通，拿到可验证的收益再往下走

### 「降级为快速兜底」到底是什么意思

不是删掉，是**改角色**。它从"唯一的估值函数"变成"三个角色"：

| 角色              | 谁在用                         | 为什么还得是它                                           |
| --------------- | --------------------------- | ------------------------------------------------- |
| **① 快速兜底**      | 价值网络加载失败 / 文件缺了 / 版本不匹配     | 保证**永远有棋可下**，不会因为权重文件坏了就开不了局                      |
| **② 搜索引擎内部**    | numba JIT 内核 `nb_core.leaf` | 网络是 Python/torch，**进不了 JIT 热路径**；JIT 搜索占对弈耗时的 99% |
| **③ 自对弈产数据的对手** | `selfplay.py` 造局面用          | 老师报的"送马"正是它造的，**保留它才能复现问题、才能证明新方案真的修好了**          |

第 ③ 条最容易忽略但最重要：**它是基准**。没有基准就说不清"网络是不是真的更强"。

> ⚠️ 顺带回答老师的担心：**规则不会错。** `features_dxf.py` 里  
> `from ..engine import geometry_dxf as G` / `rules_dxf as R` —— 读的就是**三人象棋的  
> DXF 变形网格 + 专利版规则**（军帐米字格、三角区回跳、副帅、判负/出局、重复判罚）。  
> 全程没有任何标准二人象棋的假设。云端打包含整个 `server/engine/`，版本与本地一致。

## 九、AutoDL 配置速答（详版见配置手册）

**一句话：钱花在核数上，不要花在 GPU 上。**

| 项目      | 建议                                    | 为什么                                          |
| ------- | ------------------------------------- | -------------------------------------------- |
| GPU     | **RTX 3090 24G**（¥1.32/时）             | 本轮产数据 **100% 是 CPU 活**；训练 MLP 的规模太小，GPU 反而更慢 |
| CPU     | **≥12 核，最好 16 核**（选机型时**优先看这列**）      | 核数直接决定工时                                     |
| 内存      | ≥ 32 GB                               | 16 个 worker 各带棋盘 + numba 工作区                 |
| 镜像      | PyTorch 2.x / Python 3.12 / CUDA 12.1 | 依赖只有 numpy / numba / torch                   |
| 磁盘      | 数据放 `/root/autodl-tmp`                | 系统盘仅 30G 且不持久                                |
| **总花费** | **¥5 ~ ¥15**                          | 产数据 3h + 训练 10min                            |

**12 核够吗？** 够 —— 本机 12 核实测 6.2 局/秒（含争抢），10 万局约 4 小时；  
16 核约 3 小时。AutoDL 的 GPU 实例一般给 12~16 核，**挑核数多的那档**即可。

### 为什么本轮不需要好 GPU（这是个反直觉但关键的判断）

| 阶段                 | 资源           | 说明                                                                                    |
| ------------------ | ------------ | ------------------------------------------------------------------------------------- |
| ① 自对弈产数据           | **100% CPU** | numba JIT 整数/浮点搜索，GPU 全程闲置                                                            |
| ② 训练价值网络           | **CPU 更快**   | 网络 `32→64→32→1` 才 4 千参数，batch 1024；GPU 的 kernel launch 开销盖过计算。本机 6.4 万样本 CPU 只花 561 秒 |
| ③（将来）MCTS + ResNet | **这里才要 GPU** | 每步上千次网络推理，batch 上千 —— 到时再上 4090                                                       |

⇒ 现在买 3090 是为第③段占位。**若只做第①②段，用最便宜的卡甚至无卡模式都行。**

### 建议的推进顺序

1. **先跑 10 万局**（16 核 ≈ 3 小时，≈¥4）→ 看 AUC 能否 0.75 → 0.85+
   - 涨上去 ⇒ 瓶颈确认是数据，继续加到 30 万
   - 卡在 0.78 不动 ⇒ 瓶颈是特征或算法，**加数据没用**，直接转 Phase 3
2. 权重回来 → 我接进 `SearchBot`（方案 c：推荐 + 对弈 + 开关）
3. 用老师报的「送马」局面做**新旧对比验证**（这是唯一的验收标准）
4. 再谈 ResNet 双头 / MCTS
