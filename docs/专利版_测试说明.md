## 一、为什么要重建测试：旧测试测的是废弃引擎

项目里有两个引擎：

| 引擎 | 模块 | 谁在用 |
|------|------|--------|
| 旧引擎（三角/菱形网格） | `geometry.py` / `rules.py` / `game.py` | 无人使用（老师给了 DXF 后作废） |
| 新引擎（DXF 权威几何） | `geometry_dxf.py` / `rules_dxf.py` / `game_dxf.py` | 服务、Arena、SearchBot、eval 全部 |

而原来的 `tests/test_basic.py`、`tests/test_patent.py` **导入的是旧引擎**（`grep -c dxf` = 0）。

证据（这些断言在 DXF 引擎里根本不成立）：

| 旧测试的期望 | DXF 引擎的实况 |
|------|------|
| 炮132 沿行滑到 133~137 | 按射线走，落点 122/131/133/142/152 |
| 兵145 有 154、155 两个前方 | 一步一格，只有 155 |
| 馬112 只能走 133 | 走 121、123 |
| `B.palace[1]`（九宫） | DXF 的 Board 没有 `palace`，只有 `gong` |

**后果**：`tests/` 跑绿跑红都与线上引擎无关。上一轮改完几何预计算后我说"跑回归测试确认未破坏"——那把尺子没量到被测对象。

**处置**：旧测试移入 `tests/_旧版备份_20260924/`（不删除），新建 `tests/test_dxf.py`。

## 四、修掉的真 bug：马和象的走法重复

`side_moves()` 和 `legal_moves()` 会给出**重复着法**。

- 空盘上 135 个点位放马，**全部**出现重复落点；象在 39 个点位重复
- 随机对局扫描 **1212 个 (局面,方)** 含重复
- 初始局面恰好因为马腿/象眼被挡住才没暴露

根因：三角格子里同一对 (起点, 落点) 有**两条 1+1（或 2+2）路径**——

```
馬112 → 121 ：可走腿 111，也可走腿 122
象113 → 131 ：可塞眼 112，也可塞眼 123
```

判定必须走"任一腿/眼为空即可"（否则规则就错了），但**着法只能记一次**。

修法：`_horse` / `_elephant` 各加一个 per-destination 去重集合。

验证（改造前后对比，用改造前固化的 13 局面参考样本）：

| 项 | 结果 |
|------|------|
| 参考样本里的重复条目 | 160 条 |
| 修复后漏掉的着法 | 0 个 |
| 修复后多出的着法 | 0 个 |
| 修复后随机对局 1920 次检查的残留重复 | 0 |
| 初始局面首着数 | 三方均 32（不变） |

危害：LLM 提示里"合法着法共 N 步"虚高、榜单宽度虚高、失误谱排名分位被稀释。

## 五、两个待老师定夺的问题

**① 「蹩马腿」在三角格子里比传统象棋弱**

传统象棋马腿唯一，堵住就走不了。这里同一落点有两条路径，堵一条还有另一条。这是三角格子的几何必然，不是 bug——但**要不要收紧成"两腿都堵才算蹩"以外的规则**，属规则设计问题，需老师确认（当前实现 = 任一腿通即可走）。

**② `server/engine/__init__.py` 仍在加载废弃引擎**

```python
from . import geometry, rules, game   # noqa: F401
```

实测每次导入都多花约 **23ms**（`engine.geometry` 9.8ms + `engine.rules` 4.8ms + `engine.game` 8.8ms），且会让读代码的人误以为旧引擎是入口。除已归档的旧测试外无人引用。**要不要清理，等老师指示**（未擅自改动）。

## 九、2026-09-24 深夜（第三轮）· 副帅「射杀」与照见线路的真实规模

### 9.1 老师的追问

老师局面：魏方控制的**副帅在 `215`(O5)**、蜀方**主帅在 `325`(I5)**，轮到魏方走。
老师问：「副帅**已经照见** I5 的主帅，并且这时轮到魏国走，为何魏国控制的副帅不能**射杀** I5 的主帅」

### 9.2 结论：老师对「照见」判断**正确**，但「射杀」不是规则里的动作

| 检查项 | 实测 |
|---|---|
| `line_of_sight(215, 325)` | **True** —— 同在列5 贯通纵线，中间 `225~335` 全空 ✓ 老师说得对 |
| 副帅参与见面判定？ | **否**（`not pc.get("deputy")`）⇒ 不产生"违规见面"对 |
| `facing_pairs(strict)` / `pending_judge` | 均**空** ⇒ 不触发任何处置（属《一、9》**豁免 2**） |
| 副帅合法着法 | `O6 / O4 / N5`（军帐内横竖 1 格）⇒ **`215→325` 不在其中** |
| 蜀帅贴到邻格 `225` 时 | `215→225` **立即合法** ✓ ⇒ 引擎**没有**"副帅不能吃帅"的过滤 |

**三条理由**（详见 `docs/三人中国象棋的游戏规则.md` §7.1 与 `专利版规则.md` §5.5b）：
① 《一、9》是**禁止性规则**（不得**造成**照面），不是吃子能力；
② 照面的后果机制在《一、10》是**判负**（B 帅留盘、棋子不易主），**判负 ≠ 吃帅**；
③ 副帅只「在军帐内行使帅职」= 走 1 格，**无远程能力**。

### 9.3 顺带证伪文档一条旧结论（本轮真正的"顺手修 bug"）

`docs/三人中国象棋的游戏规则.md` §9.1 原文写：

> 「**只有 6 对**，且全部落在各军帐的**行1（底边）**。帅走到军帐行2 / 行3 时永远不会"见面"。」

**实测证伪**（本轮 §2/§3/§4）：

| 项 | 文档旧说 | 实测 |
|---|---|---|
| 军帐内照见对总数 | 6 | **120**（同方 66 / 跨方 54，每两方 18，三方对称） |
| 列5 军帐 9 点 | — | **36/36 两两全照见** |

## 十、2026-09-25 · 「照见即可射杀」上线（重大规则变更）

### 10.1 ⚠️ 上一份结论（§9.2）已作废

§9.2 的结论是「**老师对"照见"判断正确，但"射杀"不是规则里的动作**」。

老师随后定夺：**这就是一条新规则，而且就是要它** ——

| 维度 | 定论 |
|---|---|
| **谁**能射杀 | 主帅 + 副帅都有（出局方那枚"就地变色"的副帅同样有） |
| **打谁** | 只能打对方**帅 / 副帅**；普通子打不动（视作被挡） |
| **后果** | **吃子**语义（帅消失 ⇒ 该方全部棋子易主 + 该方出局），**不是判负** |
| **旧条款** | 废除《一、9》「禁止照面」+《一、10》「被动见面判负」⇒ 改为「**轮到谁，谁能吃**」 |
| **线路** | 沿见面线（规则图六条跨方贯通线 ⇒ 引擎列 **4/5/6**） |

## 十一、2026-09-25（第二轮）· 斩帅口径定案：**「吃帅的棋子就地升格为副帅」**（《一、7》原文）

> 本节记录一次**口径三次翻转、最终回滚到原文**的完整过程 —— 它是"老师看实际效果再定规则"的典型案例，
> 也是"断言写不对就保护不了语义"的典型案例。

### 11.1 事情的起点

老师实战开局，让魏国的炮吃掉吴国主帅，结果——

> 「我发现有bug，我魏国的炮把吴国的主帅吃掉以后，**为何我的炮就消失了，变成了副帅**」

引擎复现（`155` 魏炮隔 `215` 炮架打 `225` 吴帥）：

| 点位 | 吃之前 | 吃之后 |
|---|---|---|
| `155` | 魏炮 | （空）← 炮消失 |
| `225` | 吴帥 | 魏方副帥（`deputy=True`，就地升格） |

→ **这不是 bug，是《一、7》原文的口径**（见 11.2）。老师当时误以为是 bug。

### 11.2 根因：规则原文与"另一种读法"在代码层撞车

规则图《一、7》原文：「**吃 A 帅的棋子为 B 方副帅**」——
字面读 = 吃帅的那枚棋子**升格**（棋子身份变更）⇒ 炮消失。**现行实现即此口径**。

但本项目早期的文档里另有一句写着「**被吃的那枚帅棋子**就地变色」。
两种读法**语义相反**（炮消失 vs 炮保留），却因为：

- 吃子动作让**炮恰好停在被吃帅的那一格**上；
- 而实现是"把落点那格替换成副帅"；

⇒ **代码层看着一样**。矛盾因此长期潜伏，直到老师盯着"炮不见了"才暴露。

### 11.3 口径的三次翻转，最后回滚到原文

| 轮次 | 规则内容 | 老师的话 |
|---|---|---|
| **初版 = 最终** | 吃帅的棋子**就地升格**为副帅（原棋子从盘上消失） | —（照《一、7》原文实现） |
| 第一改 | 吃帅的棋子**原样留盘**；被吃的帅易主为副帅、进驻军帐空位 | 「不行，**炮还是炮，不能变**，否则相当于我少了一个功能型棋子」 |
| 第二改 | **被吃的帅直接从盘上移除**（不生成副帅）；吃帅的棋子原样留盘 | 「炮留下了，然后**副帥不需要，直接移出棋盘**」<br>「**仅仅是当帅被吃的时候，移出棋盘**」← 纠正范围：不是副帅机制整个退役 |
| **回滚（最终）** | **吃帅的棋子就地升格为副帅**（炮变成副帥、留在落点） | 「等一下，**我搞错了，是我没有好好看游戏规则，的第7条，你退回原先的方式**」 |

（落在被吃帅的位置，必在 A 方军帐内），归吃帅方控制；② 该方**出局**；
③ 残兵**全部易主**给吃帅方；④ **原棋子（炮/车/兵…）从盘上消失**（身份变更、不是新造单位）。

✅ 因此这是**忠实执行《一、7》原文**、**不与原文偏离**的口径；
2026-09-24 之前那份写着「被吃帅就地变色」的旧描述才是**需要作废**的那一版。

## 十二、2026-09-25（第三轮）· 兵「过河」口径修正：「未过河不能横走，过河 = 跨过地带走纵向路线」

> 本轮是**老师实战报 bug** 驱动的：一句话问出两处**互相掩盖**的实现偏差。

### 12.1 老师原话

> 「我发现一个bug，魏国的兵在A7要过河往前走到F3，**为啥走不了**，是什么规则限制吗？」
> 「这魏国的兵A7在**没有过河（就是过祁山这个地带）之前不能横向左右行走的**」

坐标换算（`引擎号 = 方编号 + 行号 + (10 − 底边图数字)`，字母=行）：
- `A7` = 魏 row5 列3 = 引擎 **`153`**
- `F3` = 蜀 row5 列7 = 引擎 **`357`**
- `3 + 7 = 10` ⇒ 二者是**同一条纵向路线**（这正是老师"7+3=10"的推理，几何上完全正确）

### 12.2 根因：两处偏差互相掩盖

| # | 位置 | 偏差 | 表现 |
|---|---|---|---|
| A | `rules_dxf._pawn()` | `crossed = (r0 >= 5) or (not in_own)` —— 把「走到本方最内层 row5」当成**过河** | A7 的兵被**错误地允许**横走 `152`/`154` |

## 十三、2026-09-25（第四轮）· 马步两处独立 bug：「落点方用错列」+「三角区回跳只做单向」

### 13.1 老师原话

> 「马不能从 L5 到 F4，你是否没有遵守游戏规则」
>

> **两者物理距离都是 54.47**。要遵守游戏规则」

第二句是本轮的**判据钥匙**：老师**禁止用物理距离**裁定走法。`156`(魏A4) 绕棋盘中心

| ① | **过河落点方用错列** | 旧码 `_cross_sides(pa, c0)` 用**起点列**判对面方，应用**落点列 `c2`** | 车/炮沿列直走（`c2≡c0`）看不出来；**马步改列**（`Δc=±1/±2`）就张冠李戴：① `c0=5`（本方中线 = 三角区三岔）时**两个对面都接上** ⇒ 凭空多一半落点（吴 `L5(245)` 走 `(2,−1)` 本应只到魏 `A4(156)`，却把蜀 `F4(356)` 也生成 —— 实测 `245→356` 物理距离 **65.30**，是正常跨方马步 44.40 的 1.47 倍）；② 反向落点查不到 ⇒ **全盘 30 条单向马步** |

## 十四、2026-09-25（第五轮）· 马步第三处：**过河不得跨本方中线**

### 14.2 上一轮的「已知固有性质」是错的

§13.4 把残留的 **6 条单向马步** 归为「纵向通道归属不对称 ⇒ 跨方日字不再可逆（规则推论）」。

### 14.3 根因与修法

**根因**：过河落点方按落点列 `c2` 判（§13），但没约束「马在横移 2 格时**跨过了本方中线**」。

**规则依据（纯拓扑）**：过河接线**一对一** —— 底边数字和恒为 10，一条纵线只通向一个对面。
日字步的「横移 2 格」若跨过中线，即「**先换接线、再沿新接线过河**」，
一步用了两条接线，落点落在起点列**并不面对**的那一方 ⇒ 规则无据。

**修法**（`server/engine/rules_dxf.py` 过河分支加 1 行）：

```python
if (c0 - COL_MID) * (c2 - COL_MID) < 0:
    continue        # c0 与 c2 分居本方中线两侧 → 该步不成立
```

`c0 = 5`（起点在本方中线上）时 `(0)*(…) = 0` 不触发 ⇒ 两个对面都可达，
老师 2026-09-24 验过的 `156→245` 那条路保持成立。

### 14.4 判据：两条硬性质同时成立

| **120° 旋转对称破坏** | 0 处 | **0 处** ✅ |

剔除的 6 条（**无新增**，整环闭合）：
`154→254→354→154`、`156→356→256→156`
（含老师报的 `A6(154)→K6(254)` 与 `A4(156)→F4(356)`）。
两条 3-环互为 120° 旋转像 ⇒ 不可能「一边有一边无」。

## 十七、2026-09-26 · numba 加速内核（方案 ①）与静态搜索（方案 ②）落地

### 17.1 老师原话

> 「你开始做 ①，然后做②」

- **方案 ①** = 把「表构建 + 着法生成 + 叶评估 + 搜索」整条热路径**编译成机器码**（`nb_core.py`）。

### 17.2 方案 ①：numba 内核

| 项 | 结果 |
|---|---|
| 吞吐 | 3~4 万 nps → **43 万 nps**（同层数 **12~22×**） |

### 17.3 方案 ②：静态搜索（quiescence）

**要解决的问题**（水平线效应）：固定深度最后一手如果是「我吃了对方一个大子」，
评估只看结果盘面 ⇒ 看起来白赚；但对手下一步能**反吃回来**。
⇒ bot 会做"一步吃、被反吃"的亏本买卖。

**做法**（`SearchBot._qsearch` ↔ `nb_core._qsearch`，逐字同构）：

1. `plies` 用尽后不立即 `leaf`，而是进静态搜索；
2. **stand-pat**：不动手的分数就是 `leaf` ——
   max 节点 `stand >= beta` 直接返回；min 节点 `stand <= alpha` 直接返回
   （吃子**不是义务**，可以不吃，这正是与"强制延伸"的本质区别）；
3. 只展开**吃子**着法（`to in board`；`rules_dxf._can_land` 已保证不会吃己子）；
4. **排序复用 `_order`**（plies 传 0 取吃子档位）——
   不另写 MVV-LVA，因为口径一分岔两边剪枝路径就不同；
   `_order` 内部同分按 mv 降序 ⇒ **与输入顺序无关** ⇒ 与 JIT 逐位可对拍；
5. `qs` 逐次递减，`qs <= 0` 硬返回（三方棋吃子链不易自然收敛，必须设上限）。

**`qs` 取几层：实测定的 2**（`QS_DEFAULT`）。

| plies | qs | JIT 节点合计（20 个「局面·方」） | 倍数 | 改变估值的局面数 |
|---|---|---|---|---|
| 3 | 0 | 125,887 | 1.0× | — |
| 3 | 2 | 333,486 | 2.6× | **17/20** |
| 3 | 4 | 527,208 | 4.2× | **17/20**（与 qs=2 相同！） |
| 5 | 0 | 842,007 | 1.0× | — |
| 5 | 2 | 3,882,606 | **4.6×** | **15/20** |
| 5 | 4 | 16,756,928 | **19.9×** | 17/20（只多 2 个） |

> 收益递减而成本指数增长：**最贵的那两层吃子几乎不改结论**。
> 深档还要抢深度（档5/6 预算 60/120 s），`qs=4` 会让档4 从 ~8 s 涨到 ~34 s
> ⇒ 取**性价比拐点 qs=2**。

### 17.5 踩过的坑（全部写进源码注释，避免后人重踩）

1. **★ 浮点求和顺序决定论（本轮根因）**：`SearchBot._leaf` 按 `board.items()`
   （字典**插入顺序**，受 `_make/_unmake` 的 pop+重插影响）累加，JIT 按 `range(N)`
   （点位序号）—— 差 ~1e-13。棋盘 **120° 旋转对称**（开局）⇒ 大量叶值**精确相等**
   ⇒ 1e-13 翻转 `alpha >= beta` / `v > best` 这类**等值比较** ⇒ 剪枝分岔 ⇒
   HISTORY/KILLER 分岔 ⇒ 宽度截断不同 ⇒ **结果差到 Δ=4.85**。
   修法：`_leaf` 改成 `sorted(board.items())`（顺带解决了"同一局面连搜两次结果不同"），
   并加 `_verify_leaf_order.py` 守这条。
2. **numba 递归入口**：从 Python 解释器**直接**调递归 njit（`_search`）会报
   `unresolved symbol`，或**跑一阵后整进程 SEGV**（44 次 `plies=5` 必崩，
   `NUMBA_BOUNDSCHECK=1` 也不抛 `IndexError` —— 根本不是越界）。
   必须经一个**非递归 njit**（`_node`）转手：**njit 调 njit** 才是受支持路径。
3. **常量折叠**：模块级全局 numpy 数组（宽度表/工作区）在 njit 里被编译期内联
   ⇒ 运行期改它**完全无效**（实测把 `WIDTH_T` 从 0 改到 100000，节点数一模一样）。
   ⇒ 一切"运行期可调的东西"必须**作函数参数**传（`WIDTH` / `QSMAX` / `QMVB`）。
4. **`search_root` 的 `nodes` 语义**：`search_root` 开头 `CTX[0]=0; CTX[1]=0`
   ⇒ JIT 返回的 `nodes` 是**本层节点数（每层重置）**，而 Python 的 `_root_search`
   是**累计**。`_choose_jit` 曾因此把累计值覆盖成本层值 ⇒ 时间外推的 ratio 失准。
5. **JIT 首次调用含编译**：任何"计时类"断言（如难度档 ⑫ 的"1 s 预算不超 2.5 s"）
   都必须**先预热**，否则测到的 dt 含 ~20 s 编译开销 ⇒ 误判成"卡死"。
6. **静态搜索需要独立缓冲**：静态搜索发生在 `_search(plies=0)` 分支里，
   此时 `_search(plies=1)` 仍占着 `MVB[1*MAX_MOVES:]` 且**还在循环里读它**
   ⇒ 共用缓冲会把上一层的着法表**就地改脏**。故 `QMVB` / `QSCB` 独立分配。
7. **★★★ numba `cache=True` + 递归 njit ⇒ 读磁盘缓存必 SEGV（本轮最贵的坑）**：
   `_qsearch` 是**递归** njit（递归深度由 `qs` 控制，最多 `QS_CAP` 层），
   一旦把它的编译产物写进磁盘缓存，**下一个进程读回缓存时会 `Segmentation fault`
   （`exit=139`）** —— 崩点在**加载缓存**阶段（连 `warmup()` 都打印不出来），不是跑逻辑。
   对照实验（每次都先清 `__pycache__/nb_core.*.nbi|nbc`，再连跑 3 次）：

   | 配置 | 第 1 次（冷编译） | 第 2 / 3 次（读缓存） |
   |---|---|---|
   | 全部 `cache=True`（含 `_qsearch`） | ✅ | ❌ SEGV |
   | 只给 `_qsearch` 单独去 cache | ✅ | ❌ 仍 SEGV |
   | **全模块去 cache** | ✅ | ✅ **连跑 3 次 exit=0，结果逐位相同** |

   ⇒ 处置：`nb_core.py` 里 **9 处 `@njit(cache=True)` 全部改成 `@njit`**。
   代价是每次进程启动多约 **15 s** 全量编译（服务用 `app.py` 后台线程预热，用户无感；
   测试脚本每次多 15 s，换来不再随机崩进程）。
   若要恢复 cache，必须先把 `_qsearch` 改成**非递归（显式栈）**并重跑本表门禁。

   > ⚠️ **排查纪律**（这次差点误判）：SEGV 最初与"三个进程同时在跑"同时出现，
   > 于是被误记为"并发编译导致"。真因是缓存本身 ——
   > **现象与"并发"同时出现时不要急下因果结论，要用「清状态 + 单进程连跑 N 次」做对照实验。**

## 十八、2026-10-01 · 悔棋「连带退回」口径 + 重启续局

### 18.1 悔棋计数口径（老师原话）

> 「注意当我魏国点悔棋的时候，其它方不算悔棋次数，但是其它方要退回一步，
>  只有魏国算一次悔棋次数。否则不合理」

**为什么旧实现不合理**：三方棋回合是 `魏→吴→蜀→魏…`，「轮到我走」时**最后落子的其实是对手**。
旧 `undo_last()` 只撤最后一步 ⇒ 魏方点悔棋撤的是**蜀方**的棋，还白扣蜀方一次机会，
撤完仍然轮到魏走 —— 悔棋等于没悔，还把对手的次数吃掉了。

**新口径**：撤到 `target` 方（＝点悔棋的那一方）**自己上次落子之前**：

| 场景 | 撤回手数 | 扣谁 |
|---|---|---|
| 魏刚走完就点悔棋 | 1（＝旧行为，不误伤） | 魏 1 次 |
| 轮到魏、吴蜀已各走一步 | 3（蜀+吴+魏） | **只扣魏 1 次**，吴蜀一次都不扣 |
| 显式指定 `army=N` | 撤到 N 上次落子之前 | 只扣 N 1 次 |
| 观战档（`human_armies` 为空） | 1（兜底＝旧行为） | 最后落子方 1 次 |

- `army=None` 的推定：优先「**人类席位里最近落过子的一方**」（＝人类按的按钮，撤自己的棋），
  无人类席位时退回"最后落子方"。
- 实现：`Match._undo_plan()` 统一算 `(target, n)`，`undo_last()` 与 `snapshot()` 共用
  （`/api/state` 因此能如实预告 `undo_who` / `undo_rollback`，前端按钮提示不再笼统写"撤回最后一步"）。
- 门禁 `tests/_verify_undo_multi.py` → **66 / 0**，其中 §⑨ 用"等价性"钉死语义：
  1 次连带悔棋 == 3 次单步悔棋（盘面完全相同），但前者只扣 1 次机会。

### 18.2 重启续局（老师原话：「如何设计能否重启网页后继续之前的棋局继续下？」）

**设计三要点**（少一个都会出事）：

| # | 要点 | 为什么 |
|---|---|---|
| ① | **默认不开**，只有 `app.py` 显式 `enable_autosave()` 才落盘 | 否则 `tests/` 里成百上千个 `Match()` 会把老师的真实存档冲掉 |

## 十九、2026-10-01（第二轮）· 规则 bug：**车/炮在军帐（米字格）内能斜走**

### 1. 老师报的现象
> 「象棋规则有bug，车在米字格魏国 军帐内为何能走斜线去吃魏国的帅？不对的。你要改。」

实测确认：魏车停在军帐中心 `D5 = 125` 时，`moves_of` 里**多出 4 个斜向落点**
`E4(116) / E6(114) / C4(136) / C6(134)` —— 车、炮在九宫中心获得了斜走能力。

### 2. 根因：军帐几何上是**米字格**
`geometry_dxf.Board._build_rays()` 按**角度**把邻接点分组生成射线。军帐（九宫）中心点
有 **8 个**几何邻接点（横 2 + 竖 2 + **斜 4**）⇒ 除了横竖两族，还多产出 **4 条斜向射线**。
而 `_rook` / `_cannon` / `PAWN_T` / `LINE_ATTACK` **全都消费 `RAYS`**
⇒ ① 车/炮能斜走；② 车/炮的**攻击表**也多出斜向威胁（污染将军判定）；
③ `line_of_sight` 把军帐中心与四角判成"共线"（两帅"照见"口径被污染）。
斜线本是**士**的专属走法（`ADV_T` / `B.gong_diag`），不该混进通用射线。

### 3. 修法：纯拓扑判据（一个角度都不碰）
```python
def _is_tent_diag(a, b):
    if a[0] != b[0]:                    # 方变 ⇒ 跨方接线/战线直通 ⇒ 放行
        return False
    return a[1] != b[1] and a[2] != b[2]   # 方不变 + 行变 + 列变 ⇒ 军帐斜线
```
在 `_build_tables()` 里，于**所有缝合之前**过滤：
```python
RAYS[p] = tuple(w for w in (_drop_tent_diag(p, r.walk) for r in rays) if w)
```
全盘实测军帐斜线 **24 步**（每方 8 条 × 3 方），过滤后 `RAYS` 里 **0 步**。

### 4. 三个坑（都真踩过）
| # | 坑 | 为什么 |
|---|---|---|
| ① | **必须在缝合之前过滤** | `_splice_front_rays()` / `_splice_row_rays()` 会把未过滤的斜线**原样保留**（行线缝合只丢"整条落在同一行内"的半截行射线） |
| ② | **必须滤掉空 `tuple`** | `_splice_front_rays()` 用 `path == fwd[:len(path)]` 匹配半截射线；空序列会**无条件命中**（`fwd[:0] == ()`）⇒ 缝合替换数被误算 |
| ③ | **不能只修车** | 斜线是 `RAYS` 层面的**结构问题**，不是某个棋种的 bug —— 修源头一处，车/炮/兵/攻击表**全部**跟着好 |

- ⚠️ 判据**不能**写成"行与列同时变化"：跨方接线（如 `156 → 254`）也是两分量同变，
  那样会把**合法的贯通线**一起砍掉。**必须先看方是否变**。
- ✅ `PAWN_T` 之所以"顺带"干净，是因为它在缝合**之后**由 `RAYS` 重建（不是用原始 `B.rays`）。
- ✅ 士的走法**完全未受影响**：`ADV_T` 走 `B.gong_diag`，与 `RAYS` 无关，军帐 4 条斜线全在。

### 5. 连带口径变更：军帐内共线对 **120 → 108**
`_verify_facing_lines.py` §3 旧断言 120（同方 66 + 跨方 54）**基于斜线存在**，已按真值改：
- **同方 54**（每方 **18** = `C(3,2) × (3 行 + 3 列)`，全部行列线）—— 原 66 / 每方 22；
- **跨方 54 不变**（列5 贯通线 9 对 + 跨方斜接列 9 对，×3 组），**对局实战判定无变化**。

### 6. 新增门禁 `tests/_verify_tent_diag.py` → **32 / 0**

## 二十二、2026-10-01（第四轮）· 文字**透明背景**：走子痕迹标签去掉白垫底

### 1. 老师原话
> 「你改一下设置：棋盘上的文字背景比如『到H5吃炮』是透明文字背景的好」

### 2. 改了什么
棋盘上带背景的只有**两类文字**（其余——色带名/三方圆名/坐标/棋子字——本来就是无底纯色）：

| 位置 | 原做法 | 现做法 |
|---|---|---|
| `_lab()` 走子痕迹标签（`起 L5` / `到 H5 吃炮` / `前到 …`） | 两层：**白色胖字垫底**（stroke `#ffffff`，宽 2.8）+ 彩色字叠印 | **单层彩色字** + 同色细描边（`st.lw * 0.95` ≈ 0.48~0.59） |
| `_drawTriZone()` 的「三角区」标签 | 两层：`tri-label-halo`（`#fffbf0` 描边 1.2）+ 金色字 | **单层金色字** + 同色细描边 0.6 |

**为什么原来会有白块**：那层白描边是 `stroke-width: 2.8`，而字号只有 3.4 —— 描边的
一半（1.4）向外扩，在浅色木盘上读起来就是**一个白色色块**，盖住网格线与色带，
观感像在棋盘上贴了张白纸。

**为什么仍留一道同色细描边**：纯 `fill` 的细字在木色底上笔画发虚；同色描边**沿字形轮廓走**，
只把笔画加实，**不产生背景填充** —— 与「透明背景」不冲突。

> 判据写成**区间**（`_verify_lastmove.js` / `_verify_move_trail.js`）：
> `0 < stroke-width ≤ 1.2`，且 `stroke === fill`（同色）且**没有任何 `fill:#ffffff` 的 text**。
> 上界 1.2 的依据：>1.5 就开始读成"块"（原值 2.8 正是被淘汰的那档）。

### 25.2 ★ 真 bug：`value_advisor.load()` 的「**假懒加载**」—— 每次启动白等 2.4 s

**症状**：`tests/_verify_difficulty.py` §⑫ 长期红（「1.0 s 预算 ⇒ 实测不超 2.5 s」，实测 **2.60 s**）。
**老师可感知的版本**：重启对弈台后**第一次搜索 / 第一次点「推荐」**莫名慢一拍。

**排查路径（值得复用的方法论）**

1. 初判"机器负载"（numba 对拍 3517 项同时跑）⇒ 机器空闲后**单独复跑仍 2.60 s** ⇒ **推翻**。
2. 写取证探针 `tests/_probe_timeout_grain.py` 量"粒度"：

   | 场景 | 实测 |
   |---|---|
   | 首次 `depth=1` | **2.43 s** / 4352 节点 |
   | 之后任意档 | **0.26 s** / 78282 节点 |

   且 `search_root.nopython_signatures` 数量**前后不变** ⇒ **排除 JIT 编译**（首次编译才会涨签名）。
3. `cProfile` 定位：`torch/nn/__init__.py` **0.923 s** + `torch/_jit_internal._overload` **1.473 s**
   ⇒ 是 **`import torch`**，不是搜索。

**根因**：`value_advisor.ValueAdvisor.load()` 旧写法**只在"权重文件不存在"时才短路**：

```python
if not os.path.exists(p):                     # ← 旧顺序：文件判定在前
    return cls(None, [], kind, lam, False, p)
from agents import value_net as VN            # ← enabled=False 也会走到这里 ⇒ import torch
```

权重的文件**一旦训出来就永远在** ⇒ 魏/蜀两席明明 `enabled=False`，照样付 `import torch` 的 2.4 s。

**修法**（顺序 = 先 `enabled`、再文件、最后才 import）：

```python
if not enabled:
    return cls(None, [], kind, lam, False, p)   # ★ 没开就绝不 import torch
if not os.path.exists(p):
    return cls(None, [], kind, lam, False, p)
try:
    from agents import value_net as VN
    ...
```

**证据（修后实测）**

- `_verify_difficulty.py` §⑫：**2.60 s → 0.13 s**（预算 1.0 s，**真在截断**）。
- 新守门探针 `tests/_probe_value_lazy.py`：**14 / 0**。四节：

  | 节 | 断言 |
  |---|---|
  | ① | 子进程里 `ValueAdvisor.load(enabled=False)` ⇒ **`torch` 不在 `sys.modules`** |
  | ② | `SearchBot(use_value=False).advisor()` ⇒ 同样不 import torch（真实入口） |
  | ③ | `enabled=True` ⇒ **必须**真 import 且拿到模型（**防修过头**） |
  | ④ | 源码级：剥注释后 `if not enabled:`(318) **<** `os.path.exists(p)`(403) **<** `from agents import value_net`(501) |

> ⚠️ **探针自身踩的两个坑（已修，留档警示）**
> 1. `①` 曾把断言写反：子进程回报的是 `adv.model is not None`（**布尔**），
>    却拿 `is None` 去判 ⇒ 永假。现改为子进程直接回报 `model is None`，语义一一对应。
> 2. `④` 的源码切片 `body.find("import value_net")` **命中了修法注释里的字样**
>    （注释里就写着 `from agents import value_net`）⇒ 得到 `import@485 < enabled@1318` 的假失败。
>    **修法：源码级断言必须先剥掉注释行再 `find`。**

**为何要留探针**：`search_bot.advisor()` 上方的注释「⚠️ 懒加载：没开时不读权重文件，也不 import torch」
**以前是假的** —— 已经改成如实说明并指向 `_probe_value_lazy.py`。这条 bug 属于
"**没人测就永远潜伏、且表现成"机器有点卡"**"的典型，必须用子进程断言钉死。

> 📌 **教训（通用）**：③ 这类"**看起来在下棋、其实大模型根本没接上**"的隐形故障，
> 唯一可靠的发现途径是 **可见性**：战报里的红色「代走」标签 + `legal_rate` 统计。
> 凡是"失败后自动兜底"的设计，都必须同时给出**用户可见的痕迹**。
