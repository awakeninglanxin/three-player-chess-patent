# 三人象棋 · 对弈评测方案（Arena）

> 起因：看到一份 LLM 棋力评测方法论，里面有四条对本项目**直接可用**的东西。
> 本文记录「照它改了什么、实测发现了什么、怎么用」。

---

## 一、那个方案说了什么，我们怎么接

| 方案里的说法 | 本项目的落地 | 状态 |
|---|---|---|
| 合法率是第一指标，不是胜率（实测：裸生成 0% / 给合法着法 100%） | `arena.summarize()` 第一列就是合法率；`match.snapshot().agents[k].legal_rate` | ✅ |
| 引擎吻合度比胜负稳定得多，要给每步打 best/blunder 标签 | 失误谱：全宽搜索给每步打分 → `best/excellent/inaccuracy/mistake/blunder` | ✅ |
| 严格时限会惩罚长考模型，所以预算要跑**曲线**不是单点 | `LLMAgent.step_log` 记每步 token 增量；`avg_prompt_tok / avg_out_tok` 出曲线 | ✅ |
| 用引擎做锚点阶梯、插值出等效棋力 | `arena.ladder()`：用 SearchBot 深度 1/2 当锚点，插值「等效搜索深度」 | ✅ |
| 「同 token / 同速度」都不是公平约束 | `think_timeout` 只作为单步上限记录，不作为评分约束 | ✅ |
| 中国象棋没有公开的 LLM 对弈基准（是空白） | 三人象棋更是空白 —— 我们这套 135 点规则引擎 + 锚点 + 裁决**是可以做榜的** | 💡 机会 |
| Laya 这类「一次前向、封闭选择题」模型**下不了棋**，需要搜索树 | 印证了我们做 `SearchBot` 而不是接 Laya 的路线；但见文末「一个有意思的组合」 | 💡 |

## 二、新增 / 改动清单

### 新增

| 文件 | 作用 |
|---|---|
| `server/agents/arena.py` | **对弈实验台**：失误谱评分、起手方轮换、6 项指标汇总、锚点阶梯 |

`arena.py` 的 API：

```python
# 1) 给一步棋打分（state 必须是落子前的局面）
grade_move(state, legal, move, grader, plies=6)
#   → {"rank":3, "loss":2.14, "loss_norm":0.03, "label":"inaccuracy", ...}

# 2) 跑一局（agents = {1:,2:,3:}）
play_game(agents, first=1, max_ply=120, mode="choice", grader=g)

# 3) 汇总成对比表 + 预算曲线数据
summarize(recs)

# 4) 起手方轮换跑多局
gauntlet(agents_factory, games_per_seat=2, grader=g)

# 5) 锚点阶梯：量出等效搜索深度
ladder(agent_factory, anchors=(1,2), games=1)

# 6) 标定失误谱分档（必须做一次，BANDS 是占位值）
calibrate_losses(recs)
```

## 三、三档赛制（很重要，结果差异巨大）

| 档 | 给模型什么 | 在测什么 | 实测合法率 |
|---|---|---|---|
| **B_choice**（本项目默认） | 棋盘 + **全部合法着法** | 纯决策质量 | **100%** |
| A_raw | 只给棋盘 | 规则内化 + 指令遵循 | 明显更低 |

切换方式：`agents.json` → `options.arena_mode` = `"choice"` / `"raw"`。

> ⚠ 两种档位的排名会不一样。**压低 A_raw 分数的不是棋力，是"会不会算规则"** ——
> 这个差值本身就是结论，不是 bug。

**另一个控制变量：历史。** 默认 `show_history=false`，即**每步只给当前局面、不给历史**。
理由：① 历史让不同模型的上下文长度不一致 = 不公平；② 模型可以靠复述上文蒙混过关，
测不出真正的状态理解。要研究「长程状态维持」时才打开。

## 四、六个指标

| # | 指标 | 含义 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **合法率** | 1 − 代走次数/请求次数 | 先筛掉「不会下棋」的 |
| 2 | **失误谱** | best/excellent/inaccuracy/mistake/blunder 分布 | 比胜负稳定得多 |
| 3 | **优+最佳率 / 大漏率** | 分布的两个端点 | 一个看稳定性，一个看下限 |
| 4 | **推进量** | 相对开局基准的进攻压强增量 + 逼近敌帅格数 | **僵持局里唯一有区分度的尺子**（见下） |
| 5 | **综合分** | 斩帅×1000 + 子力×8 + 吃子×8 + 推进 + 存活300 − 代走×20 | 回答「谁下得好」 |
| 6 | **预算** | 每步 token / 耗时，出「预算-表现曲线」 | 回答「同样资源谁更强」 |

## 五、悔棋机制（和「回退」是两件事）

这两个词以前在网页上混着显示，很容易误会，现在分开了：

| | **回退 / 代走** | **悔棋** |
|---|---|---|
| 触发 | 模型输出了**非法**着法 | 模型走出了**合法但很臭**的棋 |
| 处理 | 兜底 Bot 代走一步 | 撤回重走（消耗 1 次机会） |
| 性质 | **缺陷** —— 衡量"会不会遵守规则" | **机制** —— 衡量"给机会能不能下得更好" |
| 计数 | `wrong[]`，一直记录 | `undo_left[]`，网页勾选后启用 |
| 网页显示 | 橙色 `代走 N` | 紫色 `悔棋剩 N` |

**规则**：
- 网页勾选「允许悔棋（每方 3 次机会）」，**默认关闭**
- 每一方**各自** 3 次机会，独立计数，三方互不占用
- 两种用法：
  - **自动**：该方走出的棋被失误谱判为「失误 / 大漏」→ 自动消耗 1 次机会重走
    （重走时把原着法从候选剔除，否则模型极可能原样再走一遍 → 死循环）
  - **手动**：点「⤺ 悔棋」撤回最后一步，该方消耗 1 次机会
- 悔棋会一并回滚局面、战报、失误谱统计；**但不会抹掉 `wrong[]`** ——
  「模型确实输出过非法着法」是模型行为的事实，悔棋撤掉的是棋，不该把这件事也擦掉
- 对局结束、没有存档、机会用完、替别人悔棋 → 都会被拒绝并给出原因

## 六、实测发现（比代码本身更值钱）

### 1. 三人棋在准完美对弈下**长期零吃子** → 胜率/子力是常数，测不出东西

实测：SearchBot 三方跑 36 手，**一个子都没掉**，三方综合分完全相同（684.0）。
锚点阶梯的 R 全部退化成 1.0，指标彻底失效。

> 这与之前推的博弈论结论一致：三人棋完美对弈必然僵持。
> 也再次说明**为什么必须用「失误谱 / 合法率」而不是「胜率」做评测**。

**解法**：造「推进量」这把尺子 —— 谁的子更逼近敌帅、对敌帅压强更大，谁就在真正下棋。
基准必须取**开局值做差**（开局三方完全对称，总压强都是 240.7，直接比绝对值等于没比）。

### 2. 「depth=2」名不副实 —— 迭代加深 + 渐进加宽会牺牲棋力换速度

`SearchBot` 的 plies=6 只展开 plies=3 排名前 14 名（`ROOT_KEEP[6]=14`），
而评分器 `rank_root` 走**全宽**。所以：

| 评分器深度 | depth1 两方 good_rate | depth2 一方 good_rate |
|---|---|---|
| 3 步（全宽） | 100% / 100% | **50%** |
| 6 步（全宽） | 88% / 88% | 75~88% |

depth2 一方在所有组合下吻合度都更低 —— **不是它棋差，是两者本就不是同一个搜索**。

**结论**：
- 想报**绝对棋力** → 必须把「depth 名义值」和「全宽 plies」分开标注，别混用
- 想测**决策质量**（LLM 这类没有自带搜索的对手）→ 这套指标才干净
- 改进方向：`ROOT_KEEP[6]=14` 可能砍得过狠，值得试 20~24 看棋力/耗时曲线

### 3. 评分器必须是「参考典」，不能只是「另一个玩家」

所以 `rank_root` 刻意**不砍宽度** —— 榜单要当干净的尺子用。
另外评分器自己带的 `noise`（根节点探索噪声）会稀释吻合度指标，
要一个干净的吻合度数字时把 noise 设 0。

## 七、怎么用

### 命令行

```bash
cd server/agents
python arena.py                       # 自检：三档评分器对比 + 失误谱 + 分位标定
```

自检输出会直接打印：合法率表、失误谱分布、归一化损失分位数（用来标定 `BANDS`）。

### 网页

```
http://127.0.0.1:8771/
```

- 排名卡里新增「失误/评分」「悔棋剩」两格
- 战报每步后面跟一个失误谱徽标（绿=最佳 → 红=大漏），鼠标悬停能看到**最优着法**是什么
- 「允许悔棋」勾选框 + 「⤺ 悔棋」按钮

### 一个有意思的组合（待验证）

方案里说 Laya 那类「一次前向、封闭选择题」的模型**下不了棋**，因为下棋要搜索树。
但本项目的 LLM 恰好走的是 **B_choice（封闭选择题）** 档 ——

> **SearchBot 负责搜索**（把 40 个合法着法用 2 层搜索排序），
> **小模型只负责在前 8 名里挑一个**。

这就是 AlphaZero 的架构：**policy（策略网络）+ search（搜索）**。
Laya / 小模型当 policy，SearchBot 当 search。
这条路值得一试：小模型的"选择"能力足够，而搜索的活交给搜索器干。

## 八、要注意的坑

1. **`BANDS` 是占位值** —— 必须用 `calibrate_losses()` 跑几十局标定一次，
   跟"锚点 Elo 必须用引擎自对弈校准"是同一件事。
2. **`composite` 必须含在场子力** —— 只算吃子收益的话，零吃子对局三方分数完全相同，
   阶梯直接退化成 1.0（踩过）。
3. **评分器深度 ≥ 场上最强一方 + 一层** —— 否则好棋会被误判成失误。
4. **相对分不能跨池比较** —— 这是本项目内的相对分，换锚点/换权重都要重标，
   别拿去跟外部 Elo 排行榜对比。
5. **自动悔棋依赖失误谱** —— 关掉 `grade_moves` 就没有评分器，自动悔棋不会生效（手动悔棋仍可用）。
