## 0. 摘要（先看这一页）

这一趟云端要解决的不是"再训一个网络"，而是**棋力优化这件事本身缺少裁判**。收场时的结论：

1. **冠军已确定并封盘**：`mlp_512_256`，`md5 8b32d63bc0830950a8f996950c8d8d43`，3,539,592 B，
   固定标尺序数 **234**（300 局，seed0=2200000）。**已同步到本地对弈台**。
2. **价值网络确实更强，可以上线**：对纯搜索 **5 个 seed 批次 5/5 同向**，
   序数合计 **641 : 378**（n=1019，p≈1e-16）。已按座位落地（吴方开、魏/蜀关）。
3. **AUC 不能选冠军**（三次独立证实）：最终冠军的 AUC 被尺子换动一次就掉 **0.0077**，
   而它"拦住"候选的差距只有 **0.0020 ~ 0.0046** ⇒ 此前六轮"候选永远追不上"是**纯尺子漂移**。

   最贵的两个：守护**每轮重抽验证集**（尺子漂移）、autopilot **把门禁当成故障腰斩守护**（活锁）。
5. **一个未解之谜被如实记录**（不编解释）：两批自对弈数据**分布几乎相同、各源自洽、

## 1. 这次云端跑的是什么

### 1.1 目标

老师的原始指令链：**「要尽量优化三人象棋的棋力」** → **「autoDL 有 GPU 和 CPU，GPU 基本空置，要好好运用」**
→ **「动手修根因（这是提升棋力最大的一笔）」** → **「A/B 对局，开干」**。

拆成三条并行线：

| 线 | 内容 | 判据 |
|---|---|---|
| **A 产数据** | 自对弈灌样本（CPU，14 → 8 worker） | 分片数 / 时间 |
| **B 训模型** | 守护循环：读全部历史数据 → 训 5 档网络 → 选优 | AUC + 稳健性 + **对局门禁** |
| **C 做裁判** | 建 A/B 对局台，裁决"到底哪份权重更强" | 胜率配对 + 序数配对 + p 值 |

### 1.2 系统架构（三层，全部在 `tools/`）

```
cloud_autopilot.sh           ← 调度层（90s 心跳：看进程、看 GPU、补拉起）
   ├── cloud_selfplay.py     ← 数据层（N worker 自对弈 → data/*.parts/partNNNNN.npz）
   └── gpu_daemon.py         ← 训练层（读全部 .parts → 训多档 → 选best → 门禁 → 落盘）
            └── arena_gate() ← 裁判层（调 tools/ab_match.py 跑 300 局固定标尺）
```

**关键设计**：

- `PartCache` 增量读片（`{(目录, 文件名)}` 去重），concat 结果缓存，**不每轮重拼**。
- **冻结验证集**（`val_frozen.json`）：一批稳定键落盘，只读；`champion.json` 带 `val` 指纹，
  指纹一变自动重测冠军。
- **冠军持久化**：`champion.json` 带 `md5` 指纹，启动时按指纹核验后接手。
- **对局门禁**：候选 AUC 只要落在 `≥ best.auc − 0.005` 就开门禁，**升不升级由真棋力说话**。
- **门禁豁免锁** `gate.lock`：门禁期间 GPU 必然 0%，autopilot 见到锁就跳过"GPU 卡死"自保逻辑。

### 1.3 资源账（实测，非标称）

| 项 | 实测值 | 备注 |
|---|---|---|
| GPU 占空比（守护自报滑动窗口） | `mean 59.0 / p50 68 / max 100`，全程均值 **46.9** | 含门禁的纯 CPU 空窗 |
| GPU 占空比（`WORKERS=8` 稳态采样） | **96.2%**（峰值 100%，**344 W / 350 W**） | 见 §4.6 |
| 自对弈并行效率 | **约 21%** | 14 进程下每 worker 4.6 s/局，单进程 0.98 s/局 |
| 单轮训练耗时 | `mlp_512_256` **253~267 s** / `mlp_1024_512` **294~320 s** / `mlp_2048_1024` **784 s** | 400 epochs |
| 单次门禁耗时 | **381 s**（第一次） / **267 s**（第二次） | 300 局，6 worker，纯 CPU |

> ⚠️ **"充分运用"的正确姿势不是堆核**：14 个 CPU worker 把 GPU 从 96% 挤到 **25.2%**，
> 而数据吞吐只从 5.69 → 5.33 局/秒（−6%）。**并行效率只有 21%，多出来的核是在互相抢内存带宽。**

## 3. 核心成果：让"换不换权重"第一次有裁判

### 3.1 问题

此前"哪个权重更好"只有 **AUC** 一个尺子。而三次独立实测都指向同一结论：

| 实测 | 结果 |
|---|---|
| 分源 AUC 0.55 → 0.60 的"改进配方" | **实战反而最差** |
| 两版权重 AUC 只差 **0.0029** | 同期实战差异远超"哪个都行" |
| 守护连六轮 AUC 单调下滑 | 后来证明**全是尺子漂移** |

⇒ **AUC 只能筛垃圾，不能选冠军。**

### 3.2 A/B 对局台的设计（`tools/ab_match.py`）

- **一局三配置**：`{A, B, C}` 同场，**座位轮转** `seat[a] = cfgs[(a-1+g%3)%3]`，每 3 局一轮转
  ⇒ 座位耦合与先手优势被完全对称化。**不能跑两批**（批次间局面不同，胜率差里全是运气）。
- **双指标**：胜率配对 + **序数配对**（赢=2 / 存活=1 / 被斩=0）。
  判和率 29~54%，**只看 `win` 会扔掉一半以上样本**。
- **健康度计数**：每步记 `last_info["plies"]`，未跑满目标层数 ⇒ 计"未跑满"；
  实测 `tl=0.2 → 0.01%`、`tl=5.0 → 0`。**>1% 就判定结果受机器负载污染，不许用来裁决。**
- **跨组裁决**（`tools/ab_pool.py`）：合并多 seed 批次 + Fisher 合并 p + 方向一致性。

### 3.3 空对照：先量噪声地板，再谈显著性

**做法**：同一配置挂两个标签（`x1` / `x2` 指向**同一文件**），两者强度**严格相等**
⇒ 它们之间的一切差异都是**纯噪声**。

| 指标 | 实测（300 局） |
|---|---|
| 胜率 | `x1` 70 : `x2` 57，**p = 0.465** |
| 序数 | 226 : 202，**p 不显著** |
| ⇒ **噪声地板** | **胜率 ±4 点 / 序数 ±24 分** |

**地板是全篇的刻度尺**：没有它，任何 p 值都没有参照物。

### 3.4 完整实验表（11 组，全部 300 局）

| 组 | 场次 | tl | 判和 | none | v1233 | 判决 |
|---|---|---|---|---|---|---|
| D1 | none, v1233, bal | 5.0 | 29% | 17.7% | **37.3%** | v 强 **p=0.000** |
| B | none, v1233, bal | 0.2 | 31% | 18.7% | **32.0%** | v 强 **p=0.007** |
| C | none, v1233, v1333 | 5.0 | 54% | 19.0% | 12.0% | 全平 |
| D | none, v1233, v1333 | 0.2 | 48% | 20.0% | 14.3% | 全平 |
| L1 | λ=0.60 | 5.0 | 42% | 232 | v35 **243** / v60 128 | **v35 ★** |
| L2 | λ=0.15 | 5.0 | 51% | 240 | v35 192 / v15 183 | v35 ≈ v15 |
| L3 | λ=0.85 | 5.0 | 16% | 293 | v35 295 / **v85 12** | **v85 灾难** |
| V1 | n1, n2, v35 | 5.0 | 34% | n1 20.0% / n2 19.7% | **26.7%** | 合并 p≈0.03 |
| V2 | n1, n2, v15 | 5.0 | 34% | n1 18.7% / n2 21.7% | **26.0%** | 同向 |
| 标尺 | n1, n2, **v1333** | 5.0 | 39% | — | **26.7% / 序数 241** | **现役更好** |
| 标尺 | n1, n2, **v1233** | 5.0 | 35% | — | 24.3% / 序数 216 | 不显著 |

**λ（价值网络混合权重）必须 ≤ 0.5**：`0.85` 是灾难（96% 被斩、平均 126 手结束）、
`0.60` 明显差、`0.35` 有数据支撑、`0.15 ≈ 0.35`。

### 3.5 5 个 seed 批次的方向一致性（最强证据）

| 批次 | v35 序数 | none 序数 |
|---|---|---|
| 1 | 144 | 72 |
| 2 | 126 | 86 |
| 3 | 126 | 72 |
| 4 | 123 | 63 |
| 5 | 122 | 85 |
| **合计** | **641** | **378** |

n = 1019，**p ≈ 1e-16**；`none` 稳在 **14.3 ~ 18.7%**（合格锚点）。
⇒ **价值网络更强，可以上线。**

### 3.6 一个反直觉但被证实三次的规律

> **三人棋的"棋力"没有绝对值，只有"对谁"。**

同一份权重 `v1233`：

| 阵容 | 战绩 | 判和率 | 解读 |
|---|---|---|---|
| `{n, v, bal}` | **32~37%**（p≤0.007） | 29~31% | 强 |
| `{n, v, v}` | 12~14%（三方全平） | 48~54% | 打平 |

**机制**：两台"和平型"同场 ⇒ 对局从 176 手拉长到 **226 手**、判和率 31% → 54%
⇒ 双方优势都变成和棋，**场上那台贪吃的纯搜索反而吃掉两家的子**。

⇒ **"同款互打打平" ≠ "它不强"**（任何策略都打不过自己的复制品）；
`{2纯+1价值}` 稳赢，`{1纯+2价值}` 优势转负。
这就是**按座位配**（吴方开、魏/蜀关）的实证依据 —— 而不是"全局一刀切"。

## 4. 抓到的 6 个真 Bug（经验核心 · 每个都足以让整晚白跑）

### 4.1 ★★★ 尺子每轮漂移 —— 最贵的一个

**现象**：守护连六轮 AUC **单调下滑** `0.6445 → 0.6447 → 0.6435 → 0.6428 → 0.6421 → 0.6403`，
冠军 `0.6467` 越来越不可达 ⇒ **一个候选都上不去**。

**根因**（`gpu_daemon.py` 旧代码）：
```python
rng = np.random.default_rng(20261001)   # ★ 注释写着"固定种子 ⇒ 各轮验证集同口径"
idx = rng.permutation(len(Y))           # ❌ len(Y) 每轮都在涨！
nval = max(1, int(len(Y) * a.val_frac)) # ❌ nval 也在涨
```
**同一个种子配上不同的长度 = 完全不同的洗牌。固定种子只固定了随机数，没固定结果。**

**决定性证据**（换尺子后立刻重测冠军）：

```
⟳ 冠军 auc 重测：0.6467 → 0.639        ← 只换尺子，掉 0.0077
被它拦住的候选差距：0.0024 / 0.0020 / 0.0032 / 0.0039 / 0.0046
                   ↑ 全部小于 0.0077  ⇒ 那六轮不是模型变差，是尺子漂移
```

**修法**（三合一）：
1. **尺子 = 一批稳定键**（片名列表）落盘 `val_frozen.json`，只读；
2. `val` 指纹写进 `champion.json`，指纹一变**自动重测冠军**；
3. **AUC 降级为筛子**（`≥ best.auc − 0.005`），升不升级**由对局门禁说了算**。

**排错过程中被证伪的三条怀疑**（都做了实测，不许靠推理）：

| 怀疑 | 实测 | 结论 |
|---|---|---|
| 两批数据**特征分布不同** | Cohen's d 中位 **0.046**，**0/32 维 > 0.2** | **否** |
| **标签被反过来** | 单特征极性 **22/32 一致**，r = +0.54 | **否** |
| 验证集**同局泄漏** | 按片切 vs 按样本切只差 **+0.0118 / +0.0051** | **否** |
| 但交叉泛化**真的崩** | sp2 `0.6284 ↔ 0.5500`；老 `0.6505 ↔ 0.5401` | **是（未解，见 §6）** |

### 4.2 冠军随重启归零

**现象**：`best` 是**进程内变量** ⇒ 守护一重启就归零 ⇒ 下一轮**无条件覆盖正式权重**
（12:33 的 0.6496 就是这样被 13:33 的 0.6467 覆盖的）。

**修法**：`champion.json`（带 `md5` 指纹）+ 启动时 `load_champion` 按指纹核验接手。
在环证据：

```
⤺ 接手上一轮的冠军：mlp_512_256 auc=0.6467（md5 8b32d63b）
```

### 4.3 ★★ autopilot 活锁：把正常工作当故障杀

**现象**：`round` 永远停在 1，门禁永远跑不完，候选永远上不了位。

**时间线（严丝合缝）**：
```
16:45:43  写候选 → 开门禁（300 局纯 CPU 对局，GPU 必然 0%）
16:47/49/51  autopilot 心跳读到 GPU 0% × 3
16:51:34  ⚠ GPU 连续 360s <5%（守护活着但不出力），重启守护
16:51:40  拉起第 2 次 ⇒ 又从「[轮 1]」开始
```

**根因**：autopilot 的自保阈值（**360 s**）与我写在旁边注释里的估计（"门禁一次约 3 分钟"）
**来自两份数据**，而实际耗时是 **381 s**（我错了 2 倍多）。
⇒ **阈值与任务耗时不同源，估错一点系统就变活锁。**

**修法**（三件）：
1. **豁免锁** `gate.lock`（`try/finally` 保证删除）；autopilot 见到锁就跳过自保判据；
2. **陈旧锁兜底**（>2400 s 自动删，防守护被 kill 后 autopilot 永久失明）；
3. **把真实耗时打进日志** —— 下一个阈值由在环数据说话，不由估算。

**在环证据（逐 30 s 采样一箭四雕）**：

```
17:15:41 🔒LOCK 门禁完成=0 重启=1    ← 已跑 5分05秒
17:16:41 🔒LOCK 门禁完成=0 重启=1    ← ★ 6分05秒，已越 360s 阈值，重启仍=1
17:17:11   ---- 门禁完成=1 重启=1    ← 完成、锁删除、重启仍=1
```
```
⚖ 门禁结束，本次耗时 381s（autopilot 自保阈值 360s；超了就靠 gate.lock 豁免）
⚖ 门禁判决：❌ 不换 —— 候选 序数227/胜166 vs 冠军 序数234/胜160 ⇒ Δ序数 -7（门槛 +25）
[轮 2] …                              ← round 1 → 2，死锁解除
```

### 4.4 `load_champion` 是死代码

**现象**：为治 §4.2 写的 `load_champion`，**定义完整、行为正确、单测全绿 —— 但全文件零调用点**。
`best` 每次重启仍是 `None`，只靠"现场封冠军"兜底盖住（副作用：每遇挑战白跑一次标尺）。

**教训**：**单元测试对死代码永远是盲区**。守门人只能是**结构断言**。
新探针 `tests/_probe_champion.py` 第 1 项就是 **AST 扫描"调用点存在"**。

### 4.5 冻结验证集吃光训练池（"先冒烟再长跑"抓到）

**现象**：冒烟第二轮打出 `验证 52,182 / 训练 0`，AUC 掉到 **0.503**（纯噪声）。

**根因**：第一版"按行数均匀抽样"在**文件数少时退化** —— 每个文件被重复命中、去重后**全员入选**。

**修法**：改成"按片均行数估要抽几片 + 片轴等间距取"。
**同时冒烟也证明了幂等性**：三轮打印的尺子指纹与来源构成**逐字相同**。

> 这次是"先冒烟再长跑"纪律**第二次**救下整晚（第一次见铁律 157）。

### 4.6 GPU 被 CPU 饿住（不是 GPU 的问题）

**现象**：GPU 均值 **25.2%**（215 W / 350 W），而同期训练轮次也在变慢。

**根因**：守护的训练循环是 **Python 主导**的（小 MLP 单步 matmul 只有几十微秒，
被 `zero_grad/forward/backward/step` 的开销淹没）⇒ 它需要**被及时调度**才能持续喂 GPU。
14 个 CPU 满载的自对弈 worker 一挤，训练循环就被饿住 ⇒ **GPU 真的闲着**。

**实测两点（同机、同守护，只改 worker 数）**：

| 自对弈 worker | 数据吞吐（心跳算） | GPU 占空比 |
|---|---|---|
| 14 | 780→794 片 / 123 s = **5.69 局/秒** | **25.2%**（峰 76%，215 W） |
| **8** | 818→831 片 / 122 s = **5.33 局/秒** | **96.2%**（峰 100%，**344 W**） |

⇒ **吞吐只掉 6%（心跳粒度内等同），GPU 涨 71 个点。**
理由：自对弈并行效率只有 ~21%，那 6 个核本来就是白扔的。

### 6.1 ★ 铁律 170：两批数据互相预测不了（机制未查明）

**现象**：逐维分布漂移**极小**（Cohen's d 中位 0.046 / 最大 0.146 / 0/32 维 >0.2）⇒

| 训练源 | 同源 AUC | 跨源 AUC | 落差 |
|---|---|---|---|
| `sp2.parts` | 0.6284 | 0.5500 | −0.078 |
| `selfplay_150k.parts` | 0.6505 | 0.5401 | −0.110 |

**分布相同、各源自洽、却互相预测不了** —— 这不是"难"，是**同一组特征在两个源里对应了不同的标签映射**。
已被排除：分布不同 / 标签翻转 / 同局泄漏。

**剩下线索**（未验证，**不编解释**）：
- 所有**单特征 AUC 中位数只有 0.50** ⇒ 信号全在**交互项**里，线性诊断看不见；
- `selfplay_150k.parts` 目录**混了多次运行的分片**（`.json` 只承认 4.55 M，目录里 ~1070 万），**来历没记账**；
- 分源 AUC 长期稳定在 `sp2 ≈ 0.558 / 老数据 ≈ 0.653`，**恰好是老数据那半在单干**。

**可复现探针**：`tools/_diag_sources.py`（分布）、`_diag_label.py`（标签映射）、`_diag_leak.py`（泄漏）。
