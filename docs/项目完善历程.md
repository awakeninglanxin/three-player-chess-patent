## 二、逐版展开

### V0.1 · 引擎骨架：把一张专利图变成可判定的网格（09-22）

**做了什么**：棋盘不是标准象棋盘，是**三方 Y 形拼合的变形网格** —— 135 个点、开局 48 子（1 帅 + 2 车马炮象士 + 5 兵）。
建 `geometry_dxf`（点位/邻居/坐标标签）+ `rules_dxf`（7 张走法表 + 射线表 + 见面线）。

**根因（第一个坑，后来升为最高优先级铁律）**：

- 原图 `docs/专利版棋盘原图.jpg` 顶边字母是**旋转 180° 印**的（肉眼读成 `O N M L K`），高倍裁切才读得对。
- **格距 13~24 不等**（DXF 变形）⇒ **长度与夹角没有任何判据意义**。
- 代价是铲掉一批用几何角度写的判据。`ANG_TOL` 从此不许放宽：最大折角 **47.58°** > 方向族最小夹角 **35.412°**，一旦用角度判共线两者就串味。

**被什么守住**：`tests/_verify_rays_topology.py` 带 **AST 扫描**，防止已铲的 `_same_line / _same_angle / _leg_rank` 被写回来。

**关键常量**（权威值，`ARMY_CN` 曾被写反过）：

```
LETTER      = {1:'ABCDE', 2:'KLMNO', 3:'FGHIJ'}   # 魏 / 吴 / 蜀 的行字母
coordLabel  = LETTER[army][5-row] + (10-column)    # 引擎号 → 棋盘标签
ARMY_CN     = {1:'魏', 2:'吴', 3:'蜀'}
TRI_PTS     = {155, 255, 355}                      # 三角区三格点
```

### V0.2 · 规则定型：两个概念被砍成二值（09-24）

**定案清单**：

| 概念 | 定案 |
|---|---|
| **军帐** | 每方九宫 3×3＝9 点，中心 `{army}25`（魏 D5 / 吴 N5 / 蜀 I5） |
| **副帅** | 主帅被吃 ⇒ 残兵归吃帅方，**吃帅那枚棋子就地升格**为副帅，驻被斩方军帐 |
| **生命力** | **二值**：本方主帅是否在盘上（副帅不算主帅） |
| **战斗力** | **二值**：主帅在，或手里握着别方副帅 |
| **出局** | 唯一触发＝**主帅被吃**（判负、认输都不算） |
| **求和** | 不存在，只允许认输 |
| **残局判平** | 只剩象/士 + `STALEMATE_ROUNDS=9` 轮 + 帅不照面 |

**为什么「出局 ≠ 判负」**：若把判负也算进出局，前端会把"判负"渲染成"被斩帅" —— 这个隐患在 V0.7 果然以"幽灵副帅"的形式兑现了。

**两个坑**：

- ❌ 军帐"米字格"误把**对角线**算进共线 ⇒ 军帐内共线对虚高。修完收敛到 **108** 对。
  ⇒ 铁律：**"哪些点共线"一律以 `RAYS` 实测枚举为准，不照抄文档。**
- ❌ 吃副帅时误写 `note["eliminated"]` ⇒ 三个连锁后果：`slain+=1` 凭空 **+1000** 分、前端渲染成"斩主帅"、屏幕误报"被杀出局"。修法：按 `victim.get("deputy")` 分流成 `note["is_deputy"]`。

**被什么守住**：`test_dxf.py` **106 项** · `_verify_rule9_10.py` **52 项** · `_verify_deputy.py` 43 项等。

### V0.3 · ★ 规则大改：照见即可射杀（09-25）

**这是规则层面最大的一次改动，起因是一句提问**：

> 「魏国控制的副帅已经照见 I5 的主帅，并且这时轮到魏国走，**为何魏国控制的副帅不能射杀 I5 的主帅**？」

| 项 | 旧（禁止照面 + 被动判负） | 新 |
|---|---|---|
| 帅照面 | 违规 ⇒ 被动方判负 | **合法**，且**轮到谁谁就能吃** |
| 谁能射杀 | — | **主帅与副帅同权** |
| 打谁 | — | 只打对方**帅/副帅**（普通子挡线上则打不动、不穿透） |
| 线路 | — | 沿**见面线**（六条跨方贯通线） |
| 后果语义 | 判负（帅留盘） | **吃子**：对方帅消失 ⇒ 出局 + 残兵易主 |

**推论链**：既然照见即可射杀，"禁止照面"与"被动判负"两条同时失去意义 ⇒ 《一、10》正式**退役**。

**守得最狠的两条测试**：

- §4 跨方穷举等价：全部 135 点、**6075 个跨方点对**，`snipe_targets` 与 `line_of_sight` **100% 一致**（含"中间插一子"的对照）。
- §9 副帅当射手（10-02 补）：用真实那局 `ply 64` 的点位 `225 → 115` 逐字段复现战报。

**顺带定案的边界**：《一、9》第 3 条"独占口径" —— 只有**独占照见**的一方能吃已出局方的帅；多方争抢（三点共线）谁都不得吃。
军帐内"跨方可照见"恰 **54 对**（27 对 × 双向），起点列只落在 **4/5/6**，其中列 5 占 **27 条**。

### V0.4 · 网页化：引擎号变成人话（09-26~）

**做了什么**：`server/app.py` HTTP 接口（`/api/state /move /hint /undo /replay`）+ `web/` Canvas 棋盘 + 战报 + 回看 + 悔棋 + 推荐；
引擎号 → 棋盘坐标（`115→E5`）；**4 档 Bot**（新手 0 / 入门 3 / 进阶 6 / 大师 9 plies），默认第 2 档。
（V0.4 当时是 4 档；后续补了「宗师 12」，**现为 5 档**，见文末当前状态。）

**三个坑**：

- ⚠️ **模块级缓存在 `init()` 必须清零**（`_triActive/_lastHint/_lastHints/_lastFocus`）—— 否则"重开一局后标记永不激活"。
- 🔴 **静态资源防缓存**：`?v=__STAMP__` + `/api/state` 返回 `build`，不一致自动重载（≤3 次）—— 否则"改了前端没变化"。
- 视觉口径：棋盘文字＝**纯单层彩色字**（只 `fill`、`stroke:'none'`、`normal` 字重）。`bold` + 同色描边＝笔画加肥两层。代价是压同色棋子会吞笔画 —— 已认可。

**唯一硬标准**：视觉改动必须**截真实网页**（puppeteer-core + 本机 Chrome），截前冻帧 + 回读 `getComputedStyle`。

### V0.5 · AI 第一步：一个"送马"质疑改变了技术路线（10-01）

**起点是这个质疑**：

> 「我认为你一开始推荐让右车往前走了一步，不对，这样，马里面就容易被蜀的炮干掉，相当于马白送。你分析一下为何这样，**给我理由**」

**复核结论：质疑完全正确**。蜀炮 H2 打魏马 E8 这条线**开局就已存在**：

- 车还在 E9 时，被吃后魏能 `E9→吃E8炮` 兑子（马 4 ↔ 炮 4.5，蜀还亏）⇒ 蜀不敢吃；
- 车走 `E9→D9` 后与 E8 既不同行也不同列，**够不着** ⇒ 马**净丢** ⇒ 白送。

**根因不在深度，在估值的权重结构**：旧 `eval` 的 10 个计分项**没有一个测"我的子会不会丢"**。

| 局面 | 旧 `eval` 对魏方评分 | 新特征"悬子值" |
|---|---|---|
| 开局，车 E9 保着马 E8 | **+36.96** | 0.0 |
| 车走 `111→121`（让开、马无人保） | **+37.87（反而涨了）** | **4.0（一个马的整价）** |

算到分量级：车往前挪一步边际 **+0.91**，白丢一个马只值 **−0.40** ⇒ 引擎认为"贴近敌帅"比"保住马"划算。
（`close1` 贴敌帅一步给 **400** 分，`material` 权重仅 **0.10** —— 两者量纲不同，不构成严格倍数关系，
但足以说明量级悬殊。旧日志里"差 1000 倍"是粗估，此处按原始数字陈述，不作倍数断言。）
第二层缺陷：`material` 是「我 − **最强的那一个**对手」⇒ 吃弱者的子对吃子方贡献 **0**。
让蜀方自己搜到 **12 plies**，"白吃马"仍只排 **第 37/44** ⇒ **瓶颈从来不是深度。**

**由此得出的原理性结论（本项目最重要的一句）**：

> **换 AlphaZero 治不了送马。** value head 只是「特征 → 胜率」的映射；
> **特征里没有"我的子正被白吃"这一维，网络就学不出来。**

所以第一步是**补特征**而不是换算法：`features_dxf.py` **32 维**（旧 10 项 + 新增 **12 维"子力安危"**）；`value_net.py` 出 `LogiNet`（可解释）+ `MLPNet`（能打）。

**上线门槛（踩坑后加的）**：用开局 44 手合法着法两两比较，特征 L∞ < 0.10 却给 |ΔP| > 0.05 记一次"矛盾"。

| 模型 | 矛盾对数 | 判决 |
|---|---|---|
| `logi` | **0 / 946** ✅ | 过 |
| `mlp`（800 局版） | **148 / 946** ❌ | **不许上线** |

**两个坑**：标准化放大（加 `SD_FLOOR=0.10` 锁 10 倍，同一对 P 差 **0.208 → 0.061**）；
小样本让系数翻符号（`my_hanging_val` 24 局学成 **+4.72**，800 局才回到 **−3.27**）⇒ **不是算法问题是数据量问题** —— 这正是云端要解的。

### V0.6 · ★ 云端训练：先给"棋力"造一把不会漂的尺子（10-01~02）

**核心洞察**：**"棋力优化"这件事本身缺少裁判**。此前只有 AUC 一把尺子，而 AUC 已被三次独立实测证伪 ——
尺子漂移：最终冠军 AUC 被尺子换动一次就掉 **0.0077**，而它"拦住"候选的差距只有 **0.0020~0.0046**
⇒ 此前六轮"候选永远追不上"是**纯尺子漂移**，不是模型不行。

**三层架构**（都在 `tools/`）：

```
cloud_autopilot.sh           ← 调度层（90s 心跳：看进程、看 GPU、补拉起）
   ├── cloud_selfplay.py     ← 数据层（N worker 自对弈 → data/*.parts/partNNNNN.npz）
   └── gpu_daemon.py         ← 训练层（读全部 .parts → 训多档 → 选 best → 门禁 → 落盘）
            └── arena_gate() ← 裁判层（调 ab_match.py 跑 300 局固定标尺）
```

机型：AutoDL **RTX 3090 24G · 15 vCPU（Xeon 8358P）· 90 GiB RAM**。

**抓到的 6 个真 bug（每个都足以让整晚白跑，3 个是 AI 自己引入的）**：

| # | Bug | 后果 | 修法 |
|---|---|---|---|
| 1 | ★★★ **尺子每轮重抽验证集** | 守护连 6 轮 AUC 单调下滑，冠军永远不可达 | 冻结验证集 `val_frozen.json` + 冠军带指纹 + AUC 降级为筛子 |
| 2 | **冠军随重启归零** | 下一轮无条件覆盖正式权重 | `champion.json`（带 md5）+ 启动按指纹接手 |
| 3 | ★★ **autopilot 活锁** | 把门禁（纯 CPU）当"GPU 卡死"腰斩 ⇒ `round` 永远停在 1 | 豁免锁 `gate.lock` + 陈旧锁兜底 |
| 4 | **`load_champion` 是死代码** | 定义了、单测全绿、**零调用点** | 补调用点 + **AST 扫描** |
| 5 | **冻结验证集吃光训练池** | 打出"验证 52,182 / 训练 0"，AUC 掉 0.503 | 按片均行数估片数 + 片轴等间距取 |
| 6 | **GPU 被 CPU 饿住** | GPU 均值 25.2% | WORKERS 14 → 8 |

**"充分运用 GPU"的正确姿势不是堆核**：

| 项 | 实测值 |
|---|---|
| GPU 占空比（`WORKERS=8` 稳态） | **96.2%**（峰 100%，**344 W / 350 W**） |
| GPU 占空比（`WORKERS=14`） | **25.2%**（峰 76%，215 W） |
| 数据吞吐 | 8 worker **5.33 局/秒** vs 14 worker **5.69 局/秒**（**只差 6%**） |
| 自对弈并行效率 | 约 **21%**（14 进程 4.6 s/局；单进程 0.98 s/局） |
| 总样本 | **12,364,743**（`sp2.parts` 1,427 片 / 71,350 局 + 老数据 1,130 片） |

⇒ 多出的 6 个核在互抢内存带宽，纯白扔。

**产出与裁决**：

- 冠军 `mlp_512_256`（hidden 512×256、400 epochs、batch 16384、**11,105,318** 样本、冻结尺子 AUC **0.639**、固定标尺序数 **234**、wins 160/300），**封盘同步到本地对弈台**。
- 价值网络确实更强：对纯搜索 **5 个 seed 5/5 同向**，序数 **641 : 378**（n=1019，p≈1e-16）。
- 落地方式：**按座位配**（吴方开 λ=0.35，魏/蜀显式关）。
- 但两轮真实门禁判决 **Δ−7 / Δ−31 全拒** ⇒ 冠军从 13:33 到收场**未被替换**。
- **一个未解之谜被如实记录（不编解释）**：两批自对弈数据分布几乎相同、各自洽、却互相预测不了（交叉泛化掉 0.08~0.11）。

### V0.7 · 收尾：三处点名的问题（10-02）

**7.1 终局悔棋自救**
> 「虽然是游戏结束了，但是魏国还剩一次悔棋机会，**应该允许魏国退回到将军之前**」

原 `undo_last()` 开头 `if self._finished(): return "对局已结束"` —— 终局一律不许悔棋，就是看到的"悔棋键禁止点击"。
改为终局自救：**最后被斩的那一方**（造成当前终局者）只要还剩机会，允许退回自己上次落子前重走，悔棋后清 `winner`、对局复活。

- 第一版写成"从被斩方里往回找第一个还有机会的"，探针当场抓到荒唐结果（魏用完还让更早出局的吴退了 34 手）⇒ 改成**只认最后被斩方**。
- 三种情形仍拒：判和/超时终局、被斩方机会用完、胜方点悔棋。
- 顺带挖出既有 bug：存档快照经 JSON 往返 `{1:0}→{"1":0}`，读回没归一化 ⇒ 悔棋回滚 `KeyError:1`。**"重启续局 + 终局悔棋"是第一条必然跨存档用悔棋快照的路径。**

**7.2 副帅登记表去残留（幽灵副帅）**

`ply 64` 那局：驻吴帐的蜀副帅 `225` 射杀魏帥 `115`，就地升格为代表新方的副帅，旧登记 `{2:…}` 没人注销
⇒ 盘上只剩 1 枚副帅、登记表却有 2 条 ⇒ 前端多显一条**幽灵副帅**。

- 修法：`patent.prune_deputies(s)` 注销"盘上已无对应副帅"的条目；`refresh_combat()` 先收敛账本再算战斗力。
- ⚠️ 判据**不能用 `pos`**（副帅在帐内走动后 `pos` 从不更新，全工程无人维护）—— 会把活着的副帅误注销。用 `home`。
- 探针含**证伪自检**：把 `refresh_combat` 换回修复前版本，断言确实留 2 条 ⇒ 证明探针抓得到真问题。

**7.3 推荐默认档 12 → 9 plies**
> 「**网页 AI 推荐用 9 plies，12 用的时间太长了**」

**两批独立标定互相矛盾，一并留档**：

| 批次 | 样本 | 结论 |
|---|---|---|
| 批一 `_bench_ply_sat.json` | 2 个局面 | 9 选的手在 12 榜单里排第 6/8、第 5/8 ⇒ 判"9 不够" |
| 批二 `_analyze_gold.py` | **16 个局面** | 6→9 中位 ratio **3.54**（12/16 真变招）值钱；**9→12 ratio 仅 1.00、噪声 45%、耗时 ×24** ⇒ 判"9 是饱和点" |

批二样本量大一个数量级，且与体感（12 太慢）一致 ⇒ **默认取 9**。这也印证 V0.5：瓶颈是估值不是深度，换默认档只改速度。

### V0.8 · 上线与可调：从"能跑"到"能给别人看"（10-25）

> ⚠️ **这一段此前没有任何文档记录** —— `版本升级日志.md` 停在 V0.7（10-02），复盘也只讲到 V0.7。

V0.7 之前的全部工作都在**本机**完成：`127.0.0.1:8771`，一个人下。V0.8 要解决的是另一个问题：

> **这台机器上跑得对，不代表别人点开链接也能看到。**

上线过程一次性暴露 6 个问题。按性质分两类：**#1~#4 只在部署环境才成立**（本机永远碰不到）；
**#5~#6 是本机就一直存在、但一直没人注意的显示缺陷**，只是这次要给人看才被盯出来。
**没有一个是玩法/规则 bug** —— 规则层到 V0.7 已经封版，这一版一个判据都没动：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 服务绑不上/访问不到 | 只硬编码 `127.0.0.1:8771` | 读 `PORT`；有 `PORT` 时绑 `0.0.0.0`；无 `PORT` 保持本机行为 |
| 2 | 平台探活失败 | 无健康检查端点 | 新增 `GET /healthz`（只回 `{"ok":true}`，不碰对局） |
| 3 | **访客点"自动对弈"纹丝不动** | `agents.json` 里 `human_armies: [1]` ⇒ 轮到魏方就等人走，ply 恒 0 | 新增 `--demo`（`SANCHI_DEMO=1`）：三方全归 Bot，**不改本机 agents.json** |
| 4 | 首页出布局、棋盘空白 | 平台反代要求每个 `/api/*` 带 `?sharecode=`，**前端 4 处 fetch 一处都没带** ⇒ 全 403 | 加 `api()` 统一透传，4 处全包 |
| 5 | 战报印出 `估值-1000000.0` | ±9e5 以上是"已被将死"的**哨兵值**，被原样印给用户 | `match.py` 加 `_score_txt()`、`search_bot.py` 加 `_score_cn()` ⇒ "估值必败（己方被将死）" |
| 6 | 战报与提示条裸印 `**粗体**` 星号 | 页面不解析 markdown | 去掉星号；再扫全页渲染文字，`**`/`__`/反引号/md 链接 **0 命中** |

**同时补上的能力：手数上限做成网页可调**

| 项 | 旧 | 新 |
|---|---|---|
| 默认值 | `agents.json` 里 `max_ply: 300` | **120**（每方 40 手） |
| 可调范围 | 改文件 + 重启 | 网页下拉框实时调 **24–300**（48 / 96 / 120 / 180 / 240 / 300） |
| 接口 | — | `POST /api/options {"max_ply": N}` → `Match.set_max_ply()` |
| 落盘 | — | **只改内存、不写回文件**（专利版 `_save_payload()` 不含 `opts`）⇒ 服务重启仍回到文件默认值 |

口径提醒：**一人一手＝1 ply，三人一轮＝3 plies** ⇒「120 手」＝每方 40 手。打满上限仍分不出胜负时按综合实力分排名：
**斩帅×1000 + 在场子力×8 + 吃子×3 + 存活 300 − 回退×20**。

**两个排版真 bug（只有真截图才看得出来的那种）**：

| 现象 | 根因 | 修法 |
|---|---|---|
| 右侧战报面板**八成留白**，只显示 2 条 | `.log` 写死 `max-height:78px`，而左列把 grid 行撑到 **483px** | 宽屏 `flex:1` + 上限 **440px**。<br>⚠️ 第一版写 `max-height:none` 是错的：grid 行高取两列内容大者，战报不限高会把整行**反撑到 1192px（整页 2595px）**，页面被拉长一倍 |
| 第一排控制行全挤在一起 | `index.html` 第一个 `.controls` **从未闭合**（31 开 30 合）⇒ 后续所有控制行都成了它的 flex 子项 | 补 `</div>`，31 开 31 合 |
| 390 宽横向溢出 **210px** | `.scoreboard` 三栏每卡约 184px 压不下去 | 加 `@media (max-width:760px)`：改单列（剩 75px）→ 元凶变 `.float-bar` → 隐藏 `.undocnt`（剩 32px）→ 元凶变 `.ctrl-panel` → `.bottom>*{min-width:0}` ⇒ **0 px** |

**验收**：`tests/_verify_maxply.js` **37 项通过 / 0 失败**。核心判据不是"下拉框画出来了"，而是
「选 48 → 自动对弈 → **真的停在第 48 手**」；另含 sharecode 透传（CDP 抓全部 `/api/*` 请求）、接口边界、1440/390 两档排版。

**变异测试（防假绿）**：把 `self.opts["max_ply"] = n` 改成 `pass`、把 `api()` 改成永不透传 ⇒ **26 通过 / 11 失败**（`sharecode 0/3`、那一局跑满 120 手）。恢复后 37/0。

## 三、被推翻的方案（❌ 留档 —— "为什么没走那条路"同样是资产）

| 方案 | 为什么被否 |
|---|---|
| ❌ 用几何角度/长度判共线 | DXF 变形，格距 13~24 不等；最大折角 47.58° > 方向族最小夹角 35.412° ⇒ 必串味 |
| ❌ 把「判负」也算进出局 | 前端会把判负渲染成"被斩帅"（V0.7 幽灵副帅证实了这个方向的风险） |
| ❌ 《一、10》被动判负 | 照见即可射杀之后它失去意义，随 V0.3 一并退役 |
| ❌ 靠加大搜索深度治"送马" | 蜀方自己搜到 12 plies，"白吃马"仍排第 37/44 ⇒ 瓶颈是估值不是深度 |
| ❌ 换 AlphaZero 治"送马" | 特征里没有"我的子正被白吃"这一维，网络学不出来 ⇒ 先补特征 |
| ❌ 用 AUC 当唯一裁判 | 已被三次独立实测证伪；尺子换动一次掉 0.0077，比候选差距还大 ⇒ 降级为筛子 |
| ❌ 14 个 CPU worker 喂 GPU | GPU 占空比从 96% 掉到 25%，吞吐只差 6% ⇒ 多出的核在抢内存带宽 |
| ❌ 战报面板 `max-height:none` | grid 行高反被内容撑到 1192px，整页拉到 2595px |
| ❌ 终局悔棋"从被斩方里往回找第一个还有机会的" | 探针抓到荒唐结果：魏用完还让更早出局的吴退了 34 手 |
| ❌ 副帅账本用 `pos` 当判据 | `pos` 在帐内走动后从不更新，会把活着的副帅误注销 ⇒ 用 `home` |

## 四、贯穿全程的三件方法论资产

1. **规则唯一权威源** —— `docs/三人中国象棋的游戏规则.md`，一切判据以它为准；
   但"**哪些点共线**"以 `RAYS` 实测枚举为准，不照抄文档（因为文档会漏掉军帐对角线这种细节）。
2. **每个改动都要被回归守着** —— 118 个脚本，含 **AST 结构断言**（防"已删的错代码被写回来"）
   和 **证伪自检**（把实现换回修复前版本，断言探针确实变红）。
3. **被推翻的方案也留档（标 ❌）** —— 见上表。项目里"为什么没走那条路"和"最后走了哪条路"是同等重要的资产。

**另外两条只在实践里才学到的**：

- **判据必须测"屏上的字"，且放在会出问题的那一档**。测"下拉框存在"没用，要测"选 48 是不是真停在第 48 手"。
- **假绿比假红更坏**。恒真式判据（如参数写反导致标签印成 `true`）会掩盖整批 FAIL —— 破法只有**变异测试**。
